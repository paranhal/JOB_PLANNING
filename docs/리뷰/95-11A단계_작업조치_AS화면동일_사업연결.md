## 사업 매칭 근본 원인

HTTP `POST /workboard/tasks`(work_type=project_work, `project_id` 존재)는 **처음부터 `work_tasks.project_id`를 저장**한다. `GetTask` JOIN의 `ProjectName`도 조직 조건으로 NULL이 되지 않는다. `ListWorkPickProjects`는 archived/complete(및 cancelled)만 제외하고 조직 무관이다. 타 조직 사업·hold 상태 사업도 저장된다.

체감 증상(「사업이 안 붙는다」「예전 화면이다」)의 원인은 저장 로직이 아니라 아래였다.

| 후보 | 결과 |
|------|------|
| ① Alpine `x-model` vs `name=project_id` POST | HTTP 재현에서 `project_id`가 그대로 저장됨. 등록 팝업 목록에 도서관공사·SI구축·보류사업 표시, 완료·보관은 제외. |
| ② 저장 후 `UpdateTask`/배치가 `project_id`를 비움 | 재현 테스트에서 저장 직후·일정표·상세·조치 GET까지 사업명 유지. 덮어쓰기 없음. |
| ③ `GetTask` JOIN이 org로 NULL | `ProjectName=도서관공사` 확인. |
| ④ `ListWorkPickProjects` status 불일치 | `archived`/`complete`만 제외하고 있었음. `cancelled`도 제외하도록 맞춤. hold는 목록·저장 가능. |
| ⑤ 등록 팝업에 기대 사업 없음 | O04(사업 0건 조직)도 조직 무관 목록을 본다. 「등록된 사업이 없습니다」는 잘못된 기대였음(95-9A Q3). |
| 조치 화면에서 사업 변경 불가 | **맞음.** 95-11 화면에 연결 UI가 없었다. 이번에 `POST .../action/project` 추가. |
| 구 화면(`/workboard/tasks/:id`)으로의 진입 | **맞음.** 아래 목록. 조치 화면처럼 보이는 상세(제목 「작업 조치」)로 들어가 사업 연결을 못 한 경우가 있다. |

수정 전후:

| 항목 | 전 | 후 |
|------|----|----|
| 등록 POST 사업 | 이미 저장됨 | 동일. 재현 테스트로 고정 |
| 조치 화면 사업 | 표시만, 변경 없음 | ▸ 사업 연결·변경, 연결/해제, 이력 한 줄, `project_site_id` 재계산 |
| 「조치」 링크 | 일부 `/workboard/tasks/:id` | 작업은 `/action` |

## 화면 구성

`project_work_action.html`을 AS 셸로 교체. 부분 템플릿은 복사하지 않고 `as/_action_parts.html` · `_action_attach.html`(ref/redirect 파라미터) · `_photo_zoom.html` 재사용.

- 헤더: ←, WT 번호, 뱃지 조치+상태, 부제 사업명·일일업무, ▸ 사업 연결·변경, 작업 보기, 다음 처리(대기/이관/취소/대기 해제/잠금 해제)
- 좌측 카드 3: 작업 및 사이트 정보 / 작업 내용 / 과거 작업 이력(같은 사이트, 없으면 같은 사업, 조직 격리, 현재 제외, 최대 5)
- 우측: 조치 내역(처리담당자+직접입력, 근무구분 **기본 없음**, 작업 구분, 작업 대상 분류(장비 L1, 없으면 숨김), 사유, 완료일시, 조치내용, 해당 없음, 자재), 첨부, 결과 **완료/추가조치 필요/이관**, 확인
- 이력 표, 하단 고정 저장 바 + 버전
- 대기·취소는 결과 라디오에 없음
- 키워드 후보는 이번 제외

080: `work_tasks.target_category_id`, `work_reason`. 시드 없음. down은 컬럼 유지(SQLite DROP 불안정).

첨부 사진 최대 3장(`work_task` 이미지). 문서는 `ref_type=work_task`.

## 브라우저

로컬 `:8080`은 이 단계 반영 전 프로세스일 수 있어, 구성·사업 연결은 HTTP 테스트로 확인했다. 운영 `app.db`·`server/data`는 열지 않았다. 배포 후 SI사업팀관리자 계정으로 ①등록(사업 선택)→카드/상세/조치에 사업명 ②조치에서 해제·재연결 ③AS 조치와 나란히 구성 ④완료/추가조치/이관, 다음 처리 대기·취소 ⑤모바일에서 좌측이 위로 쌓이고 하단 바 고정 — 을 TEST DB에서 확인할 것. 비밀번호는 이 문서에 적지 않는다.

## 질문 (확정 전 임의 구현 범위)

**(a) 「작업 대상 분류」 원천**  
장비 분류표(`equipment_categories`) **대분류(parent 없음, 활성)** 를 현재 조직 기준으로 썼다. 조직에 분류가 없으면 항목을 숨긴다. 전 조직 공용 분류가 필요하면 알려 달라.

**(b) AS 키워드 사전 재사용**  
기술적으로는 `as_keyword_*`를 작업 조치내용에 붙일 수 있다. 사전 문구가 AS 장애 중심이라 이번 단계는 넣지 않았다. 작업용 사전을 따로 둘지 말해 달라.

**(c) 후속 작업 생성 시 원 작업 상태**  
95-11과 같이 원 작업은 `partial_complete`(추가조치 필요). 후속은 `waiting`. 원 작업을 완료로 닫지 않는다.

**(d) 조치완료보고서(작업)**  
만들지 않았다. AS 「조치완료보고서」 자리는 비우지 않고 버튼을 생략했다. 필요하면 다음 단계에서 양식을 정해야 한다.
