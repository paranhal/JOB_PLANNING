### 발견: 드라이버의 가짜 `Z`

이 SQLite 드라이버는 `DATETIME` 컬럼을 문자열로 읽을 때 저장 숫자 뒤에 `Z`를 붙인다(`2026-11-06 16:48:45` → `2026-11-06T16:48:45Z`, 시험으로 확인). 그대로 UTC 순간으로 취급해 KST로 바꾸면 **모든 화면이 +9시간** 된다. 그래서 `Z`·`+00:00`은 **숫자를 그대로 KST로** 읽고, 0이 아닌 오프셋(`+09:00` 등)만 순간을 지켜 KST로 바꾼다. `TestParseTimeRoundTripThroughDriver`가 실제 드라이버 경로로 이를 지킨다.

### 왜 마이그레이션이 아니라 도구인가 (cutoff 문제)

과거 행(UTC)과 새 행(KST)은 문자열만으로 구분되지 않아 **cutoff(저장 코드가 KST로 바뀐 빌드가 처음 기동한 시각)** 가 필요하다.
0단계 구현은 `app_settings.95_133_local_now_since`(표식)를 cutoff로 썼는데, 이 표식은 **95-161A(11-09)부터 `db.go`가 이미 기록**한다. 그런데 INSERT를 현지 시각으로 바꾼 수정(`CreateActivity`·mailer·notify)은 그때 커밋되지 않았다. 운영 이미지가 그 수정을 언제 포함했는지는 코드로 알 수 없으므로(`build.sh`는 작업 트리를 복사한다), 표식을 cutoff로 쓰면 **그 사이의 UTC 행이 보정에서 빠지거나**, 이미 KST인 행이 **두 번 +9**될 수 있다.
그래서 cutoff를 **사람이 명시**하게 했다(기본값 없음). 표식 값은 참고로만 출력한다. 기동 시 자동 반영도 하지 않는다.

구분 원리: UTC로 저장된 행의 숫자는 cutoff(KST)보다 **최소 9시간 이르고**, KST로 저장된 행은 cutoff **이후**이므로 `created_at < cutoff` 만 +9시간 한다. 정확히 cutoff와 같은 행은 KST로 보고 그대로 둔다.

### 운영에서 실행하는 순서 (사용자가 직접)

1. `deploy/data/app.db` **백업**.
2. 저장 코드가 KST로 바뀐 빌드를 운영에 올려 **처음 기동한 시각(한국 시각)** 을 정한다. 모르면 운영 화면에서 가장 이른 「KST로 보이는」 조치 이력의 시각을 본다.
3. **미리보기**(쓰기 없음):
   ```bash
   go run ./cmd/utcshift133 -db data/app.db -cutoff "2026-11-12 07:06"
   ```
   표별 대상 건수와 가장 이른·늦은 시각이 나온다. 「대상」의 가장 늦은 시각이 cutoff보다 9시간 이상 이르면 정상이다. 참고로 나오는 `95_133_local_now_since`와 크게 다르면 cutoff를 다시 확인한다.
4. **반영**(한 트랜잭션, 한 번만):
   ```bash
   go run ./cmd/utcshift133 -db data/app.db -cutoff "2026-11-12 07:06" -apply
   ```
   두 번째 반영은 `app_settings.95_133_utc_shift_done` 마커로 거절된다. 되돌리려면 백업을 복원한다.

대상 표: `work_activities`, `mail_outbox`, `sms_outbox`의 `created_at`.
