## ①-1 빌드가 일어나는 곳과 local_now

서버는 소스를 컴파일하지 않는다. 로컬 맥에서 `./deploy/build.sh`가 `server/Dockerfile`로 linux/amd64 이미지를 만들고 `deploy/server-app.tar`로 저장한다. Dockerfile은 `server/` 작업 디렉터리를 `COPY . .` 한 뒤 `go build -ldflags`로 `main.buildVersion`에 `VERSION` 파일 내용을 넣는다. 운영 서버는 그 tar를 `docker load`만 한다.

`3c32ff9`에 이미 들어 있는 코드가 두 심볼을 호출한다. `db.go`의 `markLocalNowSince`, `account_lifecycle.go`의 `model.LocalNowString`. 정의는 아직 커밋되지 않은 파일에만 있다.

| 파일 | 빌드 | 커밋 |
|------|------|------|
| `server/internal/model/local_now.go` | `go build ./cmd/server`에 필요 | 대상. 없으면 깨끗한 체크아웃은 컴파일되지 않음 |
| `server/internal/repository/local_now_mark.go` | 같음 | 같음 |
| `local_now_test.go`, `local_now_reserve_test.go`, `local_now_activity_test.go`, `notify/local_now_test.go`, `mailer/local_now_test.go` | 서버 바이너리에는 안 들어감. `go test`가 이 트리를 돌릴 때 같이 컴파일됨 | 구현 파일과 같이 넣는 편이 게이트 재현에 맞음 |

`server/.dockerignore`는 이 파일들을 빼지 않는다. 작업 트리에 있으면 이미지 빌드에 포함된다.

제안: 이미지를 만들기 전에 구현 파일 둘과 시험 파일 다섯을 별도 커밋으로 넣는다. 그러면 git만 받아도 컴파일되고, 이미지의 커밋 해시가 그 소스를 가리킨다. 이번 준비에서는 그 커밋을 만들지 않았다. 커밋 전까지는 아래 체크리스트의 빌드 직전 확인으로 빠짐을 막는다.

`./deploy/build.sh`는 커밋이 아닌 `server/` 작업 디렉터리를 복사한다. 지금 트리에는 메일·알림·작업함 저장소·관리 화면 템플릿 등 이번 배포와 무관한 수정도 있다. 그 상태로 빌드하면 그 수정이 이미지에 들어가고, 커밋 해시 뒤에 `-dirty`가 붙는다. `server/data/`는 dockerignore로 빠진다.

## ② 마이그레이션 리허설

원본은 운영 파일 `/home/sys2/deploy/data/app.db`가 아니다. 읽기 전용으로 받은 배포 전 백업이다.

`version=dev`, `commit=unknown`은 ldflags 없이 만든 리허설 바이너리라서 그렇다. 운영 이미지는 `deploy/build.sh`가 VERSION·커밋·시각을 넣는다. 기동 로그에 `108 project_phases apply`, `109 package_plans apply`, `110 package_events apply`, `111 package_milestones apply` 오류는 없었다. `PRAGMA foreign_key_check` 3건은 적용 전과 같고, 대상은 `as_receipts` 1278·1279·1280 → `customers`다. 이번 마이그레이션이 만든 위반이 아니다.

`AppSchemaVersion`은 72다. 108~111은 `schema_migrations`에 번호를 올리지 않고, 기동 시 `INSERT OR IGNORE`로 72를 다시 찍는다. 리허설 전후 최대값은 72, 불일치 메시지는 비었다.

같은 DB로 두 번째 기동(`PORT=8772`)도 `/version` 200이고 적용 오류 줄이 없었다. `CREATE IF NOT EXISTS`와 duplicate column 무시라 재기동은 그대로 통과한다.

실패 시 down:

- 앱은 `*.down.sql`을 실행하지 않는다. 한 문장이 duplicate column이 아닌 오류면 그 스크립트의 나머지 문을 멈추고 로그만 남긴 뒤 기동은 계속한다.
- 사본에 108을 적용한 뒤 `INSERT INTO project_phases(phase_id)`로 NOT NULL 실패를 만들었다. 표는 남았고, down은 자동으로 돌지 않았다. `108_project_phases.down.sql`을 손으로 실행한 뒤에야 `project_phases`가 없어졌고 사업·작업·사이트·고객 건수는 그대로였다.
- 적용이 끝난 사본에 down을 111 → 110 → 109 → 108 순으로 실행했다. 새 표와 단계 코드 16개가 없어지고 핵심 건수·스키마 72는 유지됐다. `work_tasks.package_id`, `work_tasks.plan_id`는 남는다. 109 down 주석대로 SQLite는 그 컬럼을 지우지 않는다.
- 새 바이너리를 다시 띄우면 108~111이 다시 적용된다. down은 그 바이너리를 멈추고 이전 이미지로 돌아갈 때만 의미가 있다. 운영 DB에는 down을 실행하지 않는다. 되돌릴 때는 DB 백업 복원과 이전 이미지를 같이 쓴다. `./rollback.sh`는 앱만 되돌리고 `data/`는 그대로라 새 표가 남는다.

리허설 서버는 종료했고 `/tmp/jp175prep`(운영 백업 사본)은 삭제했다.

## ④ 운영 서버 배포 체크리스트

대상: `ssh -p 11800 visionit`, 작업 디렉터리 `/home/sys2/deploy`, 포트 8888. 이미지 교체는 `update.sh`다. 마이그레이션 명령은 따로 없다. 컨테이너가 뜨며 `InitDB`가 108~111을 적용한다. 리허설에 쓴 `app-20261111-2300-배포전-95-174.db`는 배포 백업으로 쓰지 않는다.

### 이미지 만들기 전 (로컬)

1. `VERSION` 파일이 `95-175`인지 본다. 커밋은 `3c32ff9`.
2. 아래 두 파일이 `server/` 아래에 있는지 본다. 없으면 `go build ./cmd/server`가 실패한다.
   - `server/internal/model/local_now.go`
   - `server/internal/repository/local_now_mark.go`
3. `server/` 안의 이번 배포와 무관한 수정(메일·알림·작업함·관리 템플릿 등)을 빌드 전에 작업 트리에서 빼 둔다. `docker build`는 git 커밋이 아니라 그 디렉터리를 복사한다. 수정이 남아 있으면 커밋 뒤에 `-dirty`가 붙고 그 수정이 이미지에 들어간다.
4. `./deploy/build.sh`. 스크립트가 `BUILDX_NO_DEFAULT_ATTESTATIONS=1`과 linux/amd64를 넣는다.
5. `docker image inspect server-app:latest --format 'os={{.Os}} arch={{.Architecture}}'`가 linux/amd64인지 보고, `docker run --rm --platform linux/amd64 --entrypoint /bin/ls server-app:latest -l /app/server`로 바이너리가 tar 안에 있는지 본다.

### 배포 직전 백업 (서버, 새 파일)

앱이 떠 있는 상태에서 지금 시각으로 새로 받는다.

```sh
cd /home/sys2/deploy
BACKUP_DIR=/home/sys2/deploy/backups ./backup-db.sh 배포전-95-175
```

파일명 규칙은 `app-YYYYMMDD-HHMM-배포전-95-175.tar.gz`다. `backup-db.sh`가 `app-$STAMP-$TAG`로 만든다. 묶음 안에는 `app.db`, 있으면 `app.db-wal`·`app.db-shm`, 그리고 `sqlite3 .backup`으로 만든 `app-consistent.db`가 있다.

무결성:

```sh
mkdir -p /tmp/bak-95-175 && tar xzf /home/sys2/deploy/backups/app-YYYYMMDD-HHMM-배포전-95-175.tar.gz -C /tmp/bak-95-175
sqlite3 /tmp/bak-95-175/app-consistent.db "PRAGMA integrity_check;"
```

첫 줄이 `ok`인지 본다. 이어서 아래 건수 SQL을 정합 사본에 실행하고, 숫자를 이 배포의 기준값으로 적는다. 리허설의 66·2882·832·1101·1502는 어제 스냅샷 참고값이다. 오늘 백업 숫자가 기준이다.

```sql
SELECT '사업' AS item, COUNT(*) AS n FROM work_projects
UNION ALL SELECT '작업', COUNT(*) FROM work_tasks
UNION ALL SELECT '사이트', COUNT(*) FROM project_sites
UNION ALL SELECT '고객', COUNT(*) FROM customers
UNION ALL SELECT 'AS', COUNT(*) FROM as_receipts
UNION ALL SELECT '스키마', MAX(version) FROM schema_migrations;
```

### 교체

1. **직전 이미지 보관.** `server-app.tar`를 덮기 전에 `cp server-app.tar server-app.tar.prev-95-174`. `update.sh`도 기동 중 이미지를 `server-app:prev`와 `server-app.tar.prev`로 남긴다. tar를 먼저 덮으면 그 실행의 prev가 새 이미지가 된다.
2. **서비스 중지 → 바이너리 교체 → 기동.** 새 tar를 `/home/sys2/deploy/server-app.tar`에 두고 `./update.sh`. 순서는 이전 `/version` 출력, `docker tag server-app:latest server-app:prev`, `docker compose down`, `docker load`, `docker compose up -d`, `localhost:8888/version` 확인이다.
3. **마이그레이션.** 별도 단계 없음. 기동 로그에 `108 project_phases apply`, `109 package_plans apply`, `110 package_events apply`, `111 package_milestones apply`가 없어야 한다.

### 배포 후 확인 순서

1. **`/version`과 로그인.** `version`이 `95-175`, `commit`이 방금 빌드한 해시, `built`가 빌드 시각, `started`가 방금 시각이다. 로그인된다. 사이드바 `#app-version`이 `version 95-175 · built …`이고 하단 라벨이 `v95-175`다. `as_receipts`는 백업 때 적어 둔 AS 건수와 같다.
2. **구조 없는 기존 사업.** 수행 구조가 없는 사업 하나를 연다. 상세에 진행 상자가 없고, 일정표가 배포 전과 같이 열린다. 기존 작업·일정이 사라지거나 다른 사업으로 옮겨 있으면 아래에서 DB 복원으로 간다.
3. **확인용 사업 하나.** 새 사업을 만들고 단계, 하부 업무, 작업 계획을 넣은 뒤 사이트 1곳을 완료로 저장한다. 수행 구조 탭의 달성률, 조치 화면의 `N곳 중 M곳`, 계획 %가 서로 같다. 머리의 계획 달성률과 작업 줄의 곳수는 역할이 다르므로, 곳수 줄은 그 작업의 완료 곳수와 맞는지 본다.
4. **진행 문장.** 그 사업의 진행 보고 문장이 사업 상세에 보인다. 주간 업무 보고서 카드 머리와 업무 회의 사업별 보기 머릿글에 같은 문장이 읽기 전용으로 붙는다. 이미 저장해 둔 주간 본문은 그대로다.
5. **건수 SQL.** 백업 때와 같은 SQL을 운영 DB에 실행한다. 사업·작업·사이트·고객·AS는 백업 때 숫자에서, 방금 만든 확인용 사업·계획·작업만큼만 는다. 스키마 최대는 72다. 새 표(`project_phases`, `phase_sites`, `phase_packages`, `package_plans`, `package_sites`, `package_events`, `package_progress_daily`, `package_milestones`)는 확인용으로 넣은 행만 있다. 단계 코드 `phase_tpl_*`는 16이다. 기존 건수가 줄거나 `foreign_key_check`가 배포 전 3건(AS 1278~1280)보다 늘면 DB 복원으로 간다. 로그에 panic, `no such column`, `108 project_phases apply`가 없어야 한다.

확인용 사업·하부 업무·계획·작업 이름 앞에 `[배포확인 95-175]`를 붙인다. 예: 사업명 `[배포확인 95-175] 수행구조`. 사이트·고객은 새로 만들지 말고 기존 사이트 1곳을 쓴다. 이 데이터는 삭제하지 않는다. 지울지는 배포 후에 따로 판단한다.

### 롤백 판단

**앱만 되돌린다** (`./rollback.sh`, `data/`는 그대로).

- 프로세스가 뜨고 `/version`이 응답한다.
- 사업·작업·사이트·고객·AS 건수가 백업 때 숫자(확인용으로 더한 행을 포함한 기대값)와 같다.
- 증상이 화면·문장·권한·진행 표시에 있고, 표를 배포 직전으로 지울 필요가 없다.
- 배포 뒤에 들어온 운영 입력(AS, 작업 수정)을 남긴다.

이 경우 108~111 표와 `work_tasks.package_id`·`plan_id`는 DB에 남는다. 이전 화면에는 수행 구조가 보이지 않는다.

**DB까지 복원한다.**

- 컨테이너가 기동하지 않거나, 마이그레이션 로그에 apply 오류가 있고 새 표가 일부만 있다.
- 기존 건수가 백업 때보다 줄었다.
- `foreign_key_check`가 배포 전보다 늘었다.
- 앱만 되돌렸더니 이전 바이너리가 `no such column` 등으로 뜨지 않는다.
- 배포 이후 입력을 버리고 배포 직전 상태로 돌아간다.

절차: `docker compose down` → 방금 받은 tar의 `app-consistent.db`를 `data/app.db`로 두고 `app.db-wal`·`app.db-shm`를 지운다 → `server-app.tar.prev-95-174`를 `server-app.tar`로 두고 `./update.sh`. `backup-db.sh`가 안내하는 `tar xzf … -C data`는 wal까지 같이 푸므로, 앱이 멈춘 뒤에만 쓴다. 배포 이후 입력은 사라진다. 확인용 `[배포확인 95-175]` 데이터도 이 복원에서는 사라진다.

### down을 손으로 실행할 때

운영에서 되돌리는 방법은 DB 복원이다. down SQL은 운영 DB에 실행하지 않는다. 사본에서만, 새 바이너리를 멈춘 뒤에, 111 → 110 → 109 → 108 순으로 실행한다.

- 지워지는 것: `package_milestones`, `package_events`, `package_progress_daily`, `package_plans`, `package_sites`, `phase_packages`, `phase_sites`, `project_phases`, 단계 코드 16개.
- 남는 것: `work_tasks.package_id`, `work_tasks.plan_id`. 109 down은 SQLite에서 그 컬럼을 `DROP COLUMN` 하지 않는다. `schema_migrations` 최대도 72 그대로다.
- 새 바이너리를 다시 띄우면 108~111이 다시 적용되어 down이 무효가 된다.
- 앱은 실패해도 down을 자동 실행하지 않는다. 한 문장이 duplicate column이 아닌 오류면 그 스크립트의 나머지를 멈추고 로그만 남긴 채 기동은 계속한다.

배포하지 않은 상태로 끝낸다. 푸시, tar 업로드, `update.sh`, `AppSchemaVersion` 수정은 하지 않았다. `VERSION`만 로컬 커밋 `3c32ff9`로 올렸다.
