# 95-180 작업 계획(3단계) 마감 수정·연장 이력 — 0단계 (읽기 전용 현황)

작성: 2026-11-12. 코드 수정 없음. 근거: 95-179 구현 보고 「범위 밖」 항목.

## 현재 상태
- 작업 계획(`package_plans`)은 만들 때만 `plan_start/plan_end`를 받는다(`CreatePlan`, `PlanDraft`).
- 라우트는 만들기·상태·삭제·이동·사이트 이동·사이트 제외뿐이다(`/projects/:id/plans/...`). **마감·이름을 고치는 경로가 없다.** 그래서 연장 이력을 남길 지점도 없다.
- 이력 표 `structure_date_changes`는 `level='plan'`을 이미 받을 수 있게 만들어 뒀고, `recordEndChangeTx`가 1단계·하부 업무에서 쓰고 있다(연장만 사유 필수, 앞당김·해제는 이력만).
- 「변경내역」 화면(`/projects/:id/changes`)은 level 구분 없이 표로 나열하므로 plan 행도 그대로 나온다.
- 마감 임박 칩(179E)은 작업 계획 `plan_end`를 이미 본다. 수정 경로가 생기면 칩이 따라간다.

## 제안 (확정 아님)
1. `POST /projects/:id/plans/:planID` 추가: 이름·예정일·마감일·다음 할 일 수정. 쓰기 권한은 기존 `planContext`와 같게.
2. 마감 연장은 사유 필수(200자), 앞당김·해제는 이력만. 기록은 `recordEndChangeTx(level='plan')`. 같은 트랜잭션.
3. 화면: 작업 계획 줄에 「수정」 접기(마감 + 연장 사유 입력). 1단계·하부 업무 폼과 같은 모양.
4. 규칙: 예정일 ≤ 마감일, 완료된 계획의 마감 수정은 허용(이력으로 남김), 하부 업무·1단계 마감과 비교 제한 없음(179 결정과 동일).
5. 시험: 연장 사유 필수·앞당김 무사유·이력 1건·권한·다른 사업 계획 404·변경내역 화면 표시, 실제 브라우저 390/820/1440.

## 질문
1. 이름·다음 할 일 수정도 같이 열까(제안: 예), 마감·예정일만 열까?
2. 완료(`done`)된 작업 계획의 마감 수정을 막을까 허용할까(제안: 허용+이력)?
3. 작업 계획의 사이트 구성 변경은 이번에 건드리지 않는 것으로 맞는가?
