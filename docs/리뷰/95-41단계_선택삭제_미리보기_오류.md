# 95-41단계 — 선택 삭제 미리보기 오류 무시(0건 모달)

기준: `커서_작업지시서_95-41_긴급_선택삭제_미리보기_0건_오류무시.md`  
선행: 95-40. 실행일: 2026-10-25.

## 한 줄

선택 삭제 확인이 「0건」으로 뜬 것은 미리보기 API가 CSRF 등으로 **403 JSON `{"error":"…"}`** 를 주는데, `preview()`가 `r.ok`/`d.error`를 보지 않고 `deletable || []`만 읽어 빈 모달을 열었기 때문이다.

## §2 실제 응답 (확정)

운영 비밀번호는 문서에 남기지 않았다. 로컬 픽스처(`si_admin`, 정안초 형태 접수 묶음 6건) + 쿠키 jar로 같은 경로를 재현했다.

| 요청 | 상태 | 본문 |
|------|------|------|
| `POST /workboard/tasks/bulk-delete/preview` — `jp_csrf` 쿠키와 `csrf`/`X-CSRF-Token` 불일치 | **403** | `{"error":"보안 확인에 실패했습니다. 페이지를 새로고침한 뒤 다시 시도해 주세요."}` |
| 쿠키·토큰 일치 (로그인 후 리스트 HTML 토큰) | **200** | `deletable` 6건, `skipped` 빈 배열 |
| 첫 `GET /workboard/board?view=list` (쿠키 없음) | 200 | `Set-Cookie: jp_csrf=…; Path=/; SameSite=Lax` (**HttpOnly 아님**). 값 = `meta name=csrf-token` = `workListSelect("…")` |

**확정 원인:** 오류 JSON을 성공처럼 처리. 부가로 `jp_csrf`가 세션 쿠키와 같이 **HttpOnly**라 JS가 쿠키를 다시 읽을 수 없었고, `fetch`에 `credentials`가 명시되지 않았다. 쿠키가 없거나 화면 토큰이 오래되면 403이 나고, 사용자는 「선택 5건」 버튼 뒤에 「선택한 0건」 모달만 봤다. 「삭제」는 `delN===0`이라 비활성.

같은 CSRF 쌍(`jp_csrf` + `csrf` 폼)을 쓰는 95-38 AS 삭제는 폼 제출이라 403 HTML/플래시로 간다. 미리보기만 fetch JSON이라 95-40에서 증상이 드러났다.

## 수정

- `preview()`: `!r.ok` 또는 `d.error` → 모달 금지, `showFlashError`(문구+상태 코드, 새로고침 버튼). 네트워크 실패 동일. 선택 N인데 `deletable+skipped==0`이면 「확인 결과를 받지 못했습니다」.
- `fetch` `credentials: 'same-origin'`. 요청 직전 `jp_csrf` 쿠키 또는 `<meta name=csrf-token>`에서 토큰 재독. 403이면 `GET /csrf` 후 1회 재시도.
- `jp_csrf`를 더블 서브밋용으로 분리(HttpOnly 끄기, Path=/, SameSite=Lax, Secure는 `COOKIE_SECURE`만). 기존 쿠키가 있어도 응답에 다시 심어 속성을 맞춘다.
- 모달 제목 「선택 n건 중 삭제 delN건」. 삭제 폼은 미리보기 `deletable`이 아니라 **선택된 id**를 보낸다. 서버가 건별 판정.
- 미리보기/삭제 거부 시 `bulk-delete preview/delete deny reason=… user=… org=… n=…` 로그.

## 95-38 삭제 불가와의 관계

95-38은 목록에 삭제 UI가 없고 CSRF/권한이 영문 403으로 끝나 「삭제가 안 됨」처럼 보였다. 95-41은 **같은 CSRF 불일치**가 업무 리스트 fetch에서 빈 모달로 위장된 경우다. 오류를 화면에 드러내고 쿠키를 JS가 읽을 수 있게 맞췄다.
