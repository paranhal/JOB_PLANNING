# 90단계 보고서 — 파이프라인 수주·계약 전환 (D-96)

기준: `커서_작업지시서_90단계_파이프라인_수주계약전환.md`, D-96, 83·84단계 `/sales/:id/promote`, `SetBidResult`·`ChangeStage(direct_won)`·`CloseContracted`.

## 한 줄

파이프라인 표에 **처리** 열을 두고, 건 상태별 주 행동 하나(수주 / 계약으로 전환 / 사업 보기)를 `SalesNextActionOf` 한 함수로 판정한다. 수주·계약 팝업은 기존 단계 처리를 호출하고 새 컬럼은 만들지 않았다.

## 동작

- **판정** `server/internal/model/sales_next.go` `SalesNextActionOf(p, workProjectID, canWrite)`.
  - 발굴·제안 → 수주(직접 수주). 입찰 결과 대기 → 수주(팝업 안 실주). 수주·협상 → 계약 팝업. 계약 완료·사업관리 없음 → `/sales/:id/promote`. 전환됨 → `/projects/:id`. 실주·중단·휴면 → 없음.
  - 읽기 전용·권한 없음·view-as: `Kind`/`Label`은 남기고 `Enabled=false`, `Href` 비움. 파이프라인 템플릿은 `Enabled`일 때만 단추를 그린다.
- **수주 팝업** `GET /sales/:id/win-dialog` → `POST /sales/:id/win-confirm`. 발굴·제안은 `ChangeStage(direct_won)`, 입찰 대기는 `SetBidResult(won)`. 이후 `ApplyWonMeta`(수주일, 금액>0일 때만 `awarded_amount`). `MarkMigratedChecked`는 기존과 같이 호출. 실주는 입찰 대기에서만, 사유 필수. 성공 JSON `next=/sales?view=pipeline&ok=won`.
- **계약 팝업** `GET /sales/:id/contract-dialog` → 기존 `POST /sales/:id/close-contract`. 계약일 필수, 금액 0 가능. 성공 시 `/sales/:id/promote`. 양식을 저장하기 전에는 사업관리 사업이 생기지 않고, 처리 열은 다시 promote 링크.
- **사업 상세** 단추 문구는 그대로(바로 수주 / 계약으로 종료). 핸들러가 같은 `SalesNextActionOf`를 넘긴다.
- 칸반·`list.html`에는 단추를 붙이지 않았다(Q-2).
- CSRF 토큰은 앱에 없다. 비로그인 POST는 세션 미들웨어가 막는다. 운영 서버는 `GuardViewAsWrite`가 쓰기를 막는다.

운영·개발 DB는 코드로 고치지 않았다. CSS는 기존 토큰·클래스만 써서 `build:css`는 하지 않았다.

## 질문

### Q-1 발굴·제안에서 수주 없이 곧바로 「계약으로 전환」이 필요한지
지금은 **수주 → 계약**만 된다. 발굴 건의 처리 열은 「수주」뿐이다. 한 번에 계약까지 가는 단축은 만들지 않았다. 현업에서 입찰 없는 수의계약이 많으면 다음 단계에서 수주 팝업에 「이어서 계약」을 붙이는 편이 단계 순서를 유지하면서도 클릭을 줄인다.

### Q-2 칸반 카드·사업 목록(`list.html`)에도 같은 단추가 필요한지
이번 단계는 **파이프라인 표만**이다. 칸반·목록에는 처리 열을 넣지 않았다. `SalesNextActionOf`는 그대로 쓸 수 있으니, 필요하면 다음 단계에서 같은 `Enabled` 조건으로 붙이면 된다.

### Q-3 수주 팝업에서 수주 금액을 바꾸면 예상금액·확도에 어떤 영향이 있는지
**예상금액(`expected_amount`) 컬럼은 바꾸지 않는다.** 금액을 넣으면 `awarded_amount`만 갱신한다. 비우거나 0이면 예상금액을 유지하고 `awarded_amount`는 그대로(보통 0)다.

파이프라인 표시 금액(`SalesAmount`)은 수주·협상 단계에서 `awarded_amount > 0`이면 그 값을 쓰고, 없으면 유효 견적 합, 그것도 없으면 0이다. 발굴·제안의 가중은 예상금액×확도인데, 수주 확정 순간 단계가 입찰·수주로 바뀌므로 **가중 산식의 확도·금액 출처가 함께 바뀐다**. 확도 숫자 자체를 팝업에서 입력하지는 않는다. 기존 `ChangeStage(direct_won)`·`SetBidResult(won)` 규칙을 그대로 쓴다.

### Q-4 이미 수주/계약 처리한 건을 되돌리는 기능이 필요한지
이번 단계에서는 **만들지 않았다**. 이중 제출은 「이미 수주된 건입니다」로 거절한다. 되돌리기가 필요하면 기존 단계 변경(사유 있는 후퇴)과 맞출지, 별도 취소를 둘지 다음 단계에서 정하면 된다.
