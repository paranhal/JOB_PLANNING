# 95-189 0단계 보고 — 도서관사업팀 일정표에 타 팀 사용자(박노선) 열·일정이 보이는 문제

작성: 2026-11-13. **읽기 전용 확인.** 코드·DB·운영 서버는 건드리지 않았다(임시 DB 시험은 저장소 밖 scratch 파일로만 돌렸다). 작업지시서 본문(§2·§3)은 파일을 찾지 못해 붙여 주신 요약(§2의 두 경로)을 기준으로 했고, §3 재현 표는 아래 「재현」으로 직접 만들었다. 지시서와 다른 점이 있으면 알려 주세요.

## 결론 (한 줄)
일정표(`/workboard/register`)의 **열은 「조회된 업무에 이름이 있는 사람」** 으로 만들어지고, 업무 조회는 **업무 자신의 `org_id` 를 맨 먼저** 본다. 그래서 `org_id` 가 도서관(O01)으로 찍힌 업무에 박노선이 담당·지원자로 걸려 있거나, `org_id` 가 비어 있고 작성자가 도서관 사용자인 업무의 담당 이름이 사용자와 매칭되지 않으면 타 팀 사람이 열로 나온다. **「ListAssignable 의 org_id 빈 사용자」 경로는 박노선이 `org_id` 가 비어 있을 때만 해당한다.** 박노선의 실제 `org_id` 는 운영 DB를 볼 수 없어 확인하지 못했다(아래 확인용 조회문).

## 1. 코드 경로

### 1-1. 열이 만들어지는 곳
- `Register` ([workboard.go:179](server/internal/handler/workboard.go:179)) → 일 보기에서 `order` = `listAssignableForPicker` 이름 목록 → `buildRegisterAssigneeColumnsMembers`.
- [register_assignee_columns.go:34](server/internal/handler/register_assignee_columns.go:34): 열 = (`order` 중 그날 일정이 있는 사람) + **(`order` 에 없어도 일정에 이름이 있는 모든 사람 `extra`)**. 즉 `order` 가 도서관 사람으로 한정돼도 **조회된 업무에 이름이 있으면 열이 생긴다.**
- 일정 이름은 담당자뿐 아니라 **지원자(members)** 도 펼쳐서 센다(`expandTaskForAssigneeColumns`, [:110](server/internal/handler/register_assignee_columns.go:110)). 지원자가 타 팀이면 그 사람 열에도 같은 업무가 나온다.

### 1-2. 업무를 조직으로 거르는 곳 — `ListTasksBetweenForOrg` → `workTaskVisibleOrgSQL` ([org_sql.go:144](server/internal/repository/org_sql.go:144))
조직 판정 순서: ① 업무 `org_id` → ② 담당자 `assignee_user_id` 의 사용자 `org_id` → ③ 담당자 **이름**이 같은 사용자의 `org_id` → ④ **작성자**의 `org_id`. 첫 번째로 값이 있는 것이 그 업무의 조직이다.
- ①에 O01 이 찍혀 있으면 담당자가 어느 팀이든 도서관 일정표에 나온다.
- ①이 비어 있으면 담당자 사용자 조직(②·③)을 보지만, **담당자가 사용자와 매칭되지 않거나 그 사용자도 `org_id` 가 비면 ④ 작성자(도서관)로 떨어진다.**

### 1-3. 경로 A — `ListAssignable` 의 org_id 빈 사용자 ([user_repo.go:183](server/internal/repository/user_repo.go:183))
도서관(O01)에만 `AND (org_id=? OR TRIM(COALESCE(org_id,''))='')` 를 붙여 **`org_id` 가 빈 활성 사용자를 도서관 담당자 후보에 넣는다.** 영향:
- 담당자 선택 목록(`listAssignableForPicker`, 호출처 20여 곳: 작업 등록·AS·유지보수·휴가·공지 등)과 일정표 열 `order`.
- 입력 검증 `checkAssigneeInOrg` 도 같은 예외를 둔다([assignee_org.go:321](server/internal/handler/assignee_org.go:321): `orgID == O01 && uo == ""`). 그래서 **빈 조직 사용자는 도서관 업무의 담당·지원자로 저장된다.**
- 그 업무는 `org_id=O01` 이 찍혀 도서관 일정표에 나온다(재현 S5와 같은 결과).
- 즉 박노선이 `org_id` 가 비어 있으면(예: 계정 정리 중 사업관리팀 지정이 빠진 경우) 지금 증상과 정확히 맞는다.

### 1-4. 경로 B — 대리입력·지원자 업무의 조직 판정
- 새 업무의 `org_id` 는 **입력자의 조직** 으로 찍힌다(`assignableOrgID(c)` → [workboard.go:2071](server/internal/handler/workboard.go:2071), [:2187](server/internal/handler/workboard.go:2187)). 담당·지원자는 `checkAssigneeInOrg`/`checkAssigneeNamesInOrg` 로 **같은 조직만** 허용하므로 정상 입력으로는 타 팀 사람이 담당·지원자가 될 수 없다.
- 우회가 되는 곳:
  1. **`prev` 허용**: `checkAssigneeInOrg(..., prev)` 는 이름이 이전 담당과 같으면 검사 없이 통과한다([assignee_org.go:299](server/internal/handler/assignee_org.go:299)). 이미 타 팀 이름이 들어 있는 업무를 수정·이동(드래그 [workboard.go:1351](server/internal/handler/workboard.go:1351), 수정 [:2578](server/internal/handler/workboard.go:2578))해도 그대로 유지된다. 지원자도 `allowedPrev` 로 같다([:2587](server/internal/handler/workboard.go:2587)).
  2. **이름만 있는 담당자**: 담당자 이름이 사용자와 매칭되지 않아도 업무는 저장된다(「사용자 미등록」 칩, `TestRegisterChipsOwnOrgOnly` 가 기대하는 동작). 그 업무는 입력자(도서관) 조직이라 열이 생긴다. **이름이 박노선과 같으면 박노선 열이 된다.**
  3. **조직 없이 들어온 옛 데이터**: 지금은 운영에서 조직 없는 업무를 막지만(`CreateTask`, [wb_repo.go:1051](server/internal/repository/wb_repo.go:1051) `APP_ENV=production` 이면 오류), 과거에 만들어져 `org_id` 가 비어 있는 업무는 위 1-2의 ②③④ 판정을 탄다.
  4. 조직 보정: `org_id` 가 빈 채로 만들 때 원천(AS·점검·영업)에서 조직을 가져오고, 비개발 환경은 O01 로 채운다(개발·시험에서만).

## 2. 재현 (임시 DB, 도서관 조직관리자 화면 `/workboard/register?view=day`)
도서관 사용자(도서관담당A), 미디어팀 사용자(미디어담당B), `org_id` 빈 사용자(빈조직Z), 사용자 없는 이름 「박노선」으로 업무를 만들고 도서관 일정표 조회 결과를 봤다.

| # | 업무 저장 상태 | 도서관 일정표에 | 열 | 근거 |
|---|---|---|---|---|
| S1 | `org_id=O02`, 담당 B(O02) | 안 나옴 | 없음 | ① O02 |
| S2 | `org_id` 빈값, 담당 B(O02) 매칭, 작성자 도서관 | **안 나옴** | 없음 | ②에서 O02 |
| S3 | `org_id=O01`, 담당 B(O02) | **나옴** | **B 열** | ① 가 O01 이면 담당 팀을 안 본다 |
| S4 | `org_id=O01`, 담당 도서관A + **지원자 B** | **나옴** | **B 열**(지원 칸) | 지원자를 열로 펼침 |
| S5 | `org_id` 빈값, 담당 **빈조직Z**(org 빈), 작성자 도서관 | **나옴** | **Z 열** | ②③ 모두 빈값 → ④ 작성자 도서관 (+ 경로 A) |
| S6 | `org_id` 빈값, 담당 빈조직Z, 작성자 없음 | 안 나옴 | 없음 | 판정 값 없음 → 어느 조직에도 안 나옴 |
| S7 | `org_id` 빈값, 담당 이름만 「박노선」(사용자 없음), 작성자 도서관 | **나옴** | **박노선 열** | ③ 매칭 없음 → ④ 작성자 도서관 |
| S8 | `org_id=O01`, 담당 이름만 「미디어담당B」(사용자 ID 없음) | **나옴** | B 열 | ① O01 |

열 목록 결과: `도서관담당A · 빈조직Z · 미디어담당B · 박노선`. 담당자 후보(`ListAssignable("O01")`)는 `도서관관리자 · 도서관담당A · 빈조직Z` — **빈조직Z 가 도서관 후보에 들어 있다.** `FindAssignable(O01, 빈조직Z)` = 허용, `FindAssignable(O01, 미디어담당B)` = 거절.

## 3. 영향 범위
- **도서관(O01) 한정.** 다른 팀은 빈 조직 예외(`OrgIDLibrary`)가 없다.
- 일정표 열(일 보기), 담당자 선택 목록(작업 등록, AS, 유지보수, 휴가, 공지 등 `listAssignableForPicker` 사용처), 같은 판정을 쓰는 목록(`workTaskVisibleOrgSQL`: 일정표·진행 중 업무·칸반 등 `...ForOrg` 계열)이 같은 원인을 공유한다.
- 같은 이름 업무가 도서관 일정표에서 합쳐 보일 수 있다(이름 기준 열).
- 쓰기(수정·이동·지원자 추가)는 `prev` 허용 때문에 이미 섞인 업무는 막히지 않는다.

## 4. 확인이 필요한 것 (운영 DB 접근 금지라 직접 보지 않았다)
박노선이 어느 경우인지 알려면 읽기 전용으로 아래를 한 번 돌려 주세요.

```sql
-- ① 박노선 계정의 조직
SELECT user_id, username, full_name, org_id, role, is_active FROM users WHERE full_name LIKE '%박노선%';
-- ② 도서관 일정표에 걸린 박노선 업무의 저장 조직·작성자
SELECT task_id, title, work_date, org_id, assignee, assignee_user_id, created_by_user_id
  FROM work_tasks WHERE assignee LIKE '%박노선%'
     OR task_id IN (SELECT m.task_id FROM work_task_members m LEFT JOIN users u ON u.user_id=m.user_id
                     WHERE m.assignee LIKE '%박노선%' OR u.full_name LIKE '%박노선%')
  ORDER BY work_date DESC LIMIT 50;
-- ③ org_id 가 빈 활성 사용자(경로 A 후보 전체)
SELECT user_id, username, full_name, role FROM users WHERE is_active=1 AND TRIM(COALESCE(org_id,''))='' ;
```
- ①의 `org_id` 가 빈값 → 경로 A(+S5). 사용자 조직을 사업관리팀으로 지정하고 빈 조직 사용자를 정리하면 해소된다.
- ①이 사업관리팀인데 ②의 `org_id` 가 O01 → 업무 쪽 문제(S3/S4/S8). 해당 업무 조직 보정 또는 담당자 정리가 필요하다.
- ①이 사업관리팀, ②의 `org_id` 가 빈값 → 작성자 판정(S7).

## 5. 수정 방향 후보 (이번 단계에서는 수정하지 않음)
1. `ListAssignable`·`checkAssigneeInOrg`·`FindAssignable` 에서 도서관의 「빈 조직 허용」을 없애고, 빈 조직 사용자는 별도 데이터 정리 목록으로 보여 준다(데이터 정리가 선행돼야 도서관 담당자가 후보에서 사라지지 않는다).
2. 일정표 열은 `order`(해당 조직 담당자) 에 있는 사람만 열로 만들고, 나머지 이름은 「타 팀/미등록」 한 칸으로 모은다(`extra` 제거).
3. `checkAssigneeInOrg` 의 `prev` 허용을 「같은 이름이면서 그 사용자가 같은 조직일 때」로 좁히거나, 타 팀이 걸린 업무를 일정표에서 경고로 표시한다.
4. 데이터 보정(별도 DB 작업): 타 팀 담당·지원자가 걸린 `org_id=O01` 업무와 조직 빈 업무 목록을 뽑아 확인 후 정리.

권장 순서: 4(영향 건수 확인) → 1 → 2. 3은 정책 확인 후.
