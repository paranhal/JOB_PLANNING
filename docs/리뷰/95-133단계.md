## 1-A 재현 기록 (2026-11-06)

행정/지원 업무 `WT-003` 「95-133 시각재현」을 만들고 상태를 완료로 저장했다.

| 출처 | 값 |
|------|-----|
| 컴퓨터 시계 (브라우저 `Date`, `Asia/Seoul`) | `2026-11-06 16:48:38` KST |
| 저장 직후 sqlite `datetime('now')` | `2026-11-06 07:48:48` (UTC) |
| sqlite `datetime('now','localtime')` | `2026-11-06 16:48:48` |
| `work_activities.created_at` 원본 | `2026-11-06 07:48:45` (`WY-001`) |
| 화면 조치 이력 | `<span>2026-11-06 07:48:45</span>` · 관리자 · 완료조치 |
| 서버 로그 | `started=2026-11-06 16:44` `http://localhost:18133` |
| 프로세스 TZ | `TZ=Asia/Seoul` (Dockerfile·compose도 `TZ=Asia/Seoul`) |

**차이 = 9시간** (16:48 KST − 07:48 저장/표시). UTC/KST와 일치. 12시간(07:48↔19:48 등)은 이 화면에서 나오지 않았다.

원인(코드, 지시서와 동일): `WBRepo.CreateActivity`가 `created_at`을 넣지 않아 SQLite `CURRENT_TIMESTAMP`(UTC)가 들어간다. `ListActivities`는 문자열 그대로, `task_show.html`은 `{{.CreatedAt}}` 변환 없음. `TZ=Asia/Seoul`이어도 SQLite `CURRENT_TIMESTAMP`는 UTC다.

`work_tasks.created_at`도 같은 기본값: `WT-003` = `2026-11-06 07:48:15`. 상세는 날짜만(`Format "2006-01-02"`).

### 12시간으로 들린 이유 (재현되지 않음, 추정)

- 조치 이력은 **24시간제+초** (`2026-11-06 07:48:45`). 오전/오후 표기 없음.
- 접수 「6시 1분 → 9시 1분」은 **18:01 KST를 6시로 말한 뒤, 화면 UTC 09:01**과 맞으면 9시간이다. 이후 「12시간」은 오전/오후를 섞은 표현으로 보는 것이 맞다.
- `FormatKoreanTime`(오전/오후)는 **AS 착수·완료 시각**에만 쓴다. 행정 조치 이력에는 없다.
- `parseTime`은 `time.Parse`(naive=UTC)를 **먼저** 쓴다. `time.Now().Format`으로 넣은 naive 로컬 문자열을 다시 읽으면 화면에 **+9시간**이 된다(AS 조치 이력). 방향이 반대라 이번 9시간 지연과는 다른 버그. 확인 후 공통 함수와 같이 고칠지 물어본다.

컨테이너 TZ 미설정: 배포 이미지는 `ENV TZ=Asia/Seoul`. TZ가 비면 `time.Now()`는 UTC가 되고 `CURRENT_TIMESTAMP`도 UTC라 조치 이력은 맞을 수 있으나 AS `Format` 저장은 UTC가 된다.

## 과거 UTC 행 (보고만, 마이그레이션 금지)

운영 DB는 만지지 않았다. 로컬 재현 DB: `work_activities` 1건, 값 UTC.

**운영에서 셀 쿼리 (승인 후):**
```sql
SELECT COUNT(*) FROM work_activities;
SELECT MIN(created_at), MAX(created_at) FROM work_activities;
```

**구분:** 문자열에 타임존이 없다. 배포 시각 이전 행만 +9. 배포 이후 `CreateActivity` 수정분이 현지 시각을 넣으면 그 행은 빼야 한다.

**제안 (승인 후 별도 커밋):**
1. `created_at = datetime(created_at, '+9 hours')` WHERE `created_at < :deploy_utc_cutoff` (저장이 UTC이므로 cutoff도 UTC).
2. 멱등: `schema_migrations` 또는 `app_settings` 키 `95_133_activities_kst`. 두 번째 실행은 no-op.
3. mail/sms 기본값 컬럼도 같은 커밋 또는 후속. `work_task_delays`(localtime)는 제외.
4. 이미 현지로 들어간 행에 +9 하면 18시간이 되므로, cutoff를 코드 배포 시각으로 고정.

## 확인 요청 (구현 전 멈춤)

1. 1-B는 `CreateActivity` + 표의 mail/sms/예약 DEFAULT를 공통 `nowLocalSQL()`/`localNowString()`(`time.Now()` → `2006-01-02 15:04:05`)으로 명시 저장해도 되는지.
2. 화면 형식: 조치 이력에서 초를 빼고 `2026-11-06 16:48`로 통일할지, 저장값 그대로(초 포함) 둘지.
3. `parseTime`의 UTC-first(+9 과다)를 이번 공통 함수와 같이 고칠지, AS는 별도인지.
4. 과거 +9 마이그레이션을 승인할지(별도 커밋). cutoff는 배포 시각.

확인 전까지 코드 수정 없음.
