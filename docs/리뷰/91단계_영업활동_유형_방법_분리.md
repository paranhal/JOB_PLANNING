# 91단계 보고서 — 영업 활동 유형·방법 분리 (D-97)

기준: `커서_작업지시서_91단계_영업활동_유형_방법_분리.md`, D-97. 마이그레이션 **065**.

## 한 줄

활동의 **내용 유형**과 **방법**을 갈랐다. 등록 폼·칩·필터가 둘을 따로 쓰고, 영업 4단계와 유형을 `SalesActTypeStage` / `SalesActTypesForStage`로만 짝짓는다. **개발·운영 DB 이관은 아직 적용하지 않았다.**

## 이관 대상 건수 (읽기 전용, 승인 대기)

질의: `SELECT activity_type, COUNT(*) FROM sales_activities GROUP BY 1` (`sqlite3 -readonly`).

**Q-1 `bid`:** 위 파일 기준 **0건**. 표대로 「기타」로 두는 것이 맞다. 운영 원본을 열 수 있으면 같은 질의를 한 번 더 보면 된다.

### 적용 방법 (승인 후)

코드의 `applySalesActivitySplit91`이 `InitDB`에 붙어 있다. **승인 전에 개발 `app.db`로 서버를 켜면 이관이 실행된다.** 이번 작업에서는 개발·운영 DB를 `InitDB`로 열지 않았다. 승인되면 개발기 → 운영 순으로 서버를 한 번 기동하면 된다. 백업 표 `sales_activities_pre91`은 확인 후 삭제 여부를 정해 주시면 된다.

## 동작

- 유형 활성 7: 정보 수집 · 자료송부 · 견적제출 · 요구사항 파악 · RFP 접수 · 제안서 제출 · 기타. 방법 6: 방문·전화·이메일·온라인미팅·내부회의·기타.
- 옛 코드 visit/call/mail/online/internal/rfp/bid는 유형에서 비활성, 삭제하지 않음.
- 단계 짝: 발굴↔정보 수집, 제안↔자료송부/견적/요구사항/RFP접수, 입찰↔제안서 제출, 그 외 기타. 저장해도 **사업 단계는 안 바뀐다**.
- 폼: 유형·방법 필수, 비활성 코드 신규 거부, 단계 불일치는 경고만(`role="status"`).
- 칩: 위쪽 **유형**(단계순 7) / 아래 **방법**(6). 필터는 `type`과 `method` AND, 사업 필터와 AND.
- 이관 후 유형=기타·방법이 접촉 수단이면 뱃지 「유형 확인 필요」(Q-2).
- 진행 체크: 담당자 접촉 = 방법 방문/전화/이메일/온라인미팅. 요구사항 파악은 **제안**. 「1차 제안」→ 입찰의 **제안서 제출**.
- 주간 보고: 유형 `research,proposal,quote,rfp,bid,requirement,material,rfp_received`. **방법·기타(이관분)는 넣지 않음**(합계가 부풀지 않게).
- `work_activities.activity_type`(업무관리 GTD)는 **다른 개념, 미변경**.
- `syncWorkTask`: 제목이 비면 `유형 · 방법`으로 업무 제목을 만든다.

## 질문

### Q-1 `bid`를 기타로 둘지 제안서 제출로 볼지
확인된 DB는 **0건**. 지금은 표대로 **기타**. 운영 원본에서 건수가 나오면 그때 제안서 제출로 바꿀지 정하면 된다.

### Q-2 「유형 확인 필요」 표시
**넣었다.** 유형=기타이고 방법이 방문/전화/이메일/온라인미팅일 때 작은 뱃지. 끄려면 말씀해 주세요.

### Q-3 상단 칩 배치
한 줄에 섞지 않고 **유형 줄**(전체+7) 다음 **방법 줄**(6). 단계별 optgroup은 등록 폼에 두었다.

### Q-4 진행 체크리스트
- 발굴: 정보 입수, 담당자 접촉(방법)
- 제안: 요구사항 파악, 견적 발송, RFP 접수, 평가방법 확정
- 입찰: 제안서 제출 (옛 「1차 제안」)

상세는 입찰 단계에서도 이 줄을 보여 준다.

### Q-5 활동 저장 시 단계 자동 이동
**하지 않는다.** 대응표는 안내·필터·보고용이다.

### Q-6 방법에 「현장 점검」「박람회·세미나」
**이번엔 추가하지 않았다.** 코드 그룹 `sales_activity_method`에 넣으면 된다. 필요하면 다음 단계에서 시드만 늘리면 된다.
