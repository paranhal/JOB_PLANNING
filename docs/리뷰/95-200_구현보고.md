# 95-200 구현 보고 — 하위(실행) 업무에서 「업무 모두 종료」: 이후 일정 제외 + 상위 업무 자동 완료

작성: 2026-11-15. 푸시·배포·VERSION 변경 없음(배포는 사용자). 지시서: `Claude outputs/코드_작업지시서_95-200_…md`. 사용자 확정: 제외한 회차의 `status`를 `cancelled`로 병행(아래 §1).

## 0. 0단계 확인 결과 (변경 전, 읽기 전용)
- **운영 SQL**: 이 환경의 DB 사본이 10-25일자 구버전이라 반복 상위 업무가 1건(정책 manual, 회차 1건 scheduled)뿐이고 `WT-3581`은 없다. 운영 DB는 건드리지 않았다. 열린 회차가 있는 상위 목록과 WT-3581 상태 분포는 **운영 사본이 필요**하다(지시서 SQL은 `FILTER` 대신 `SUM(CASE…)`로 바꿔 두었다). 사본 기준 회차는 `work_date`·`due_date`가 모두 채워져 있고 날짜 없는 열린 회차는 0건.
- **`skipped`의 화면별 취급**
  - 제외하는 곳: 열린 회차 수(`CountOpenOccurrences`), 지연 목록(`collectOverdueOccurrences`), 임박 회차 건수, 진행률 분모(`CalcOccurrenceProgress`), 지연 자동 표시(`MarkPastOccurrencesOverdue`), 일정 변경 보호.
  - 제외하지 않는 곳(임시 테스트로 실측, 삭제함): 기존 방식으로 제외해도 `status` 가 `todo` 로 남아 「오늘 예정」·「진행중」 목록과 일정표(`ListScheduledOn`)에 날짜대로 계속 나온다. `status` 를 `cancelled` 로 바꾸면 「진행중」·「지연」에서는 빠지지만 「오늘 예정」·일정표에는 날짜별로 남는다(기존 동작). 주간보고·통계 쿼리에는 `skipped` 조건이 없고 `status` 만 보므로, `todo` 로 남으면 계획·이월에 계속 잡힌다.
  - → 그래서 사용자 확정에 따라 이 일괄 경로의 제외 회차는 `occurrence_status=skipped` + `status=cancelled` 로 바꾼다. 기존 개별 「제외」 폼은 바꾸지 않았다.
- **기존 이력 방식**: `logUpdate`(감사 로그)·`InsertWorkTaskProcess`(업무 처리 이력)가 있어 그대로 썼고, 지시서 4-4의 메모도 함께 남긴다.
- **알림·그룹 부수효과**: 기존 회차 완료·제외 경로(`UpdateOccurrence`)에는 알림·그룹 연동이 없다. 이번 일괄 처리도 별도 부수효과를 내지 않는다.
- **회차 날짜**: `occurrenceDate` = `work_date` 우선, 없으면 `due_date`. 둘 다 없으면 「이후」로 본다.

## 4. 한계·남은 것·질문
1. **운영 데이터 미확인**: 열린 회차가 있는 상위 목록·`WT-3581` 상태 분포는 운영 사본 SQL 결과가 필요하다. WT-3581 은 사용자가 화면에서 직접 누른다(일괄 정리 없음).
2. **`cancelled` 병행의 영향**: 제외 회차는 주간보고 계획·이월과 열린 업무 통계에서 빠지지만, 일정표와 「오늘 예정」에는 날짜별로 계속 보인다(기존 동작). 「취소」 건수 집계에는 잡힐 수 있다. 기존 개별 「제외」 폼은 그대로라 `todo` 로 남는 기존 동작이 유지된다 — 같은 문제를 개별 제외에도 적용할지 결정이 필요하다.
3. **이전 미완료 기본값**은 「함께 제외」(체크됨)로 두었다. 같은 날짜의 다른 열린 회차는 「이전」으로 분류한다(해제하면 열린 채 남도록 보수적으로). 날짜 없는 열린 회차는 「이후」로 처리한다.
4. **이력**: 감사 로그(`logUpdate`)·업무 처리 이력·제외 회차의 `not_done_reason`·상위 `complete_note` 에 사유와 처리자·날짜를 남긴다.
