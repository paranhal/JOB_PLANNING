## 0. 결론

- 「모두」를 코드 전체(UTC 기본값 179곳 + 테이블 DEFAULT 147곳)로 읽으면 일괄 치환은 위험하고 얻는 것이 작다. **사용자에게 보이는 것·날짜 집계에 쓰이는 것**만 골라서 하는 것을 권한다.
- 조사로 확인한 **사용자 가시 항목은 5종**이다. 그중 확실히 틀리게 보이는 것은 **2종**(`work_tasks.created_at`의 「업무 등록일」, 「팀장 변경 이력」 시각)이다.
- 날짜 집계는 `work_activities.created_at`(이미 KST로 쓰기 시작) 하나가 직접 영향받고, **과거 행은 95-133 보정 도구를 반영해야 일자가 맞는다.** 반영하면 과거 일자별 통계가 바뀐다(아래 §2-D).
- `updated_at`(UPDATE 시 UTC)은 건드리지 않는 것을 권한다(화면에 시각으로 나가는 곳이 없고, 같은 열에 UTC·KST가 섞이면 보정으로 구분할 수 없다).

그 밖에 확인한 것:
- 날짜를 `date(t.created_at)`로 자르는 SQL 17곳 중 대부분(`stats_work.go`, `stats_weekly.go`, `work_week_review.go`, `work_task_assets.go`)은 `COALESCE(work_date, due_date, date(created_at))`의 **마지막 대체값**이라 `work_date`·`due_date`가 비어 있을 때만 쓰인다. 영향이 작다.
- `work_task_dates.go:33·39`는 시작 시 **한 번** `receipt_date=date(created_at)`, `complete_date=date(updated_at)`로 빈 값을 채운다(백필). 이미 채워진 행에는 영향이 없다.
- `login_help.go:74`는 이미 `date(created_at,'localtime')`을 쓴다(서버 TZ가 KST일 때만 맞음 — §3-③).
- `created_at`과 `updated_at`을 서로 비교하는 코드는 찾지 못했다(`updated_at > created_at` 류 0건). 그래서 `created_at`만 KST로 바꿔도 순서·「수정됨」 판단이 깨지는 곳은 보이지 않는다.

## 2. 제안 (선택은 사용자)

### A. `work_tasks.created_at`
- 위 INSERT 경로(`CreateTask` 포함)에서 `created_at`을 `model.LocalNowString()`으로 **명시 저장**한다. `updated_at`은 이번에 건드리지 않는다.
- 과거 행은 보정 도구의 대상 표에 `work_tasks.created_at`을 추가한다(같은 cutoff 원리).
- 시험: 새 업무의 `created_at`이 KST인지, KST 00:30에 만든 업무의 「업무 등록일」이 **그날**로 나오는지(서버 TZ 3종), 보정 경계.

### B. `org_head_history.acted_at`
- INSERT 2곳에 `acted_at`을 `LocalNowString()`으로 명시하고, 화면은 `formatLocalDateTime`으로 분 단위 표시. 과거 행은 보정 도구 대상에 추가(이력이 적어 영향 작음).

### C. 미확인 4화면(표 C)
- 각각 저장 값을 확인한 뒤 같은 방식(저장 명시 + 분 단위 표시)으로 맞춘다. 저장이 이미 현지 시각이면 표시만 고친다.

### D. 보정 도구 반영 시 통계가 바뀐다
`work_activities` 과거 행을 +9시간 하면 UTC 15:00~24:00에 만든 행이 KST 다음 날로 넘어가므로 **과거 일자별 통계가 달라진다**(맞게 바뀌는 것이다). 반영 전에 사용자가 이 점을 알고 있어야 한다. 미리보기에는 표별 건수만 나오고 일자 변화는 나오지 않으므로, 필요하면 「이동하는 일자 수」를 미리보기에 추가한다.

### E. 하지 않기를 권하는 것
- `UPDATE … updated_at = CURRENT_TIMESTAMP` 일괄 치환(work_* 파일만 약 30곳, 전체 179곳): 화면에 시각으로 나가는 곳이 없고, 같은 열에 UTC·KST가 섞이면 보정 cutoff로 구분할 수 없다. `updated_at`을 KST로 쓰려면 **모든 쓰기 경로를 한 번에** 바꿔야 해서 단계로 나눌 수 없다.
- 테이블 `DEFAULT CURRENT_TIMESTAMP` 147곳 변경: SQLite는 표 재생성이 필요해 위험이 크고, 위 명시 저장으로 충분하다.

## 3. 서버 TZ에 기대는 곳 (참고)

운영은 Docker `TZ=Asia/Seoul`이라 지금은 맞지만, TZ가 비면 틀어진다.
① `time.Now().In(time.Local)` 9곳(`day_bound.go:31·35`, `workboard_home.go:20`, `work_status_repo.go:209`, `org_export.go:88`, `sales_v44_migrate.go:474` 등) — `model.KST()`로 바꿀 수 있다(작은 변경).
② `login_help.go:74`의 `'localtime'`(SQLite가 서버 TZ를 씀).
③ 95-133에서 `LocalNowString`·`parseTime`은 이미 KST 고정으로 바꿨다.
제안: 이번 단계에서 ①②를 함께 정리할지 결정이 필요하다(일 경계 함수가 오늘 날짜를 정하므로 시험 3종 TZ로 검증).

## 4. 시험 계획 (구현 시)

서버 TZ를 UTC·KST·UTC-5로 바꿔 돌린다. KST 00:30·08:59·09:00에 만든 업무의 등록일·팀장 변경 이력 시각, 보정 도구 확장(표 2개 추가) 경계·재반영 거절, 기존 `Test95_133*` 통과, 일자 통계 시험(과거 행 보정 전후). 전체 게이트 `known_failures` 변동 0.
