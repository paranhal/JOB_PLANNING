## 0. 한 줄 결론
- 지시서 §2 표는 **렌더 결과와 전부 맞다.** 2단계 하부 업무에는 이름·유형·순서·상태·삭제·다음 할 일 수정 수단이 화면에도 서버에도 없다.
- 3단계 계획의 **사이트 옮기기·제외 경로(`PlanMoveSites`, `PlanExcludeSite`)는 서버에만 있고 화면 입구가 0개**다(「확인 필요」→ **「없음」** 확정).
- 지시서에 없던 걸림돌 4가지를 찾았다(§8): 비활성 하부 업무는 화면 조회 쿼리에서 **통째로 빠진다**, 하부 업무 상태 「보류」는 **작업 등록 선택에 영향이 없다**, 대시보드·주간 보고서·업무 회의용 가벼운 트리는 **하부 업무 상태를 무시**한다, 이름 중복 기준이 곳곳에서 다르다.
- 「변경 내용 저장」(C-2)을 **한 트랜잭션**으로 하려면 저장소 함수 3개를 `*sql.Tx` 받는 형태로 나눠야 한다. 가능하지만 **작은 변경은 아니다**(§7).

## 4. `phase_packages` 컬럼이 읽히는 곳

### `status` (auto/done/hold) — 읽기는 있는데 **쓰는 곳이 없다**
| 읽는 곳 | 동작 |
|---|---|
| 수행 구조 트리 (`project_structure_tree.go` `buildPkg`) | `EffectiveStatus(status, 활동, 전부 완료)` → 「완료/보류/진행 중/완료 후보/예정」 표시 |
| 마감 임박 (`project_deadline_soon.go:41`) | `pk.status<>'done'` 인 하부 업무만 후보 |
| 작업 상세 완료 후보 안내 (`package_events.go` `PlanProgressView`) | 사이트가 전부 끝났고 `status != done` 이면 「모두 끝남」 안내 |
| 수량만 하부 업무의 작업 계획 선택지 (`tree.Options`) | `Status: pk.status` 만 전달 |
| 사업 통합 스냅샷(`structure_merge` 읽기·복원), 구조 복사 | `status` 값을 복사 |
| **쓰는 곳** | 생성 시 `'auto'`, 통합 복원 때 원값 — **화면·API 로 바꾸는 곳 없음** |

진행률은 사이트 수·수량으로만 계산하고 `status` 는 진행률 분모에 쓰이지 않는다(지시서 「보류도 분모는 그대로」와 일치).

### `is_active`
- 거의 모든 **조회가 `pk.is_active=1` 로 거른다**: 트리(`project_structure_tree.go:199`), 가벼운 트리(`package_progress.go:631`·`:456`), 작업 등록 하부 업무 목록(`PackageChoices`), 하부 업무 사이트 조회, 사이트 배지(`project_structure_badges.go`), 일자·배지·사이트 수정 대상 조회, 마감 임박, 구조 템플릿 후보.
- 쓰기 경로는 **없다**. 구조 복사(`noteInactivePackages`)와 사업 통합(스냅샷에 `is_active` 포함)만 「있을 수 있는 값」으로 처리한다.

### `seq`
- 모든 목록이 `ORDER BY pk.seq, pk.package_id`. 생성 시 `MAX(seq)+1`. 순서를 바꾸는 쓰기는 없다. 구조 복사·템플릿 적용은 `maxPkgSeq` 뒤에 붙인다.
- 1단계 `MovePhase`·계획 `MovePlan`처럼 **이웃과 seq 교환** 방식이 이미 있어 같은 패턴을 쓰면 된다. 다만 `seq` 가 중복되거나 비활성이 섞이면 이웃 계산이 어긋날 수 있다(구현 때 비활성 제외 규칙 필요).

### `next_note`
- 읽는 곳: 트리 `PkgNode.NextNote` → 진행 보고 문장 `ReportPlan.PackageNote`. `nextSentence()` 는 **계획의 다음 할 일이 모두 비었을 때만** 하부 업무의 다음 할 일을 쓴다(`model/progress_report.go:540`).
- 입력하는 곳: **없음**(0건). 즉 하부 업무 `next_note` 는 지금 항상 빈 값이다. 지시서의 「완료 후 계획으로 쓰인다는 설명」 문구는 계획이 먼저라는 규칙까지 같이 적어야 사실과 맞다.

### 영향받는 화면 전수 (값이 바뀌면)
수행 구조 화면, 사업 대시보드(마감 임박 칩·진행 줄), 업무 회의 보드(`meeting_board.go` 진행 줄·배지), 회사 주간 보고(`stats_company_weekly_ui.go` 진행 줄·배지), 작업 등록의 「수행 단계」·하부 업무 선택(`ProjectPackageChoices`), 작업 상세 「수행 단계」 라벨·완료 후보 안내(`TaskPlanLabel`, `PlanProgressView`), 사이트 배지, 구조 복사·템플릿·사업 통합.

| 사업 통합 스냅샷 | `project_merge_moves.payload` | 복원 때 하부 업무를 되살림 |

**방침 후보**
- **A (지시서 기본안)**: 실적(연결 작업·계획·계획에 묶인 사이트·수량 기록·일 이벤트)이 없으면 하드 삭제(마일스톤 시드·직접 등록 사이트·스냅샷 행 함께 삭제), 있으면 비활성만. 1단계 `DeletePhase`·`DeletePlan` 과 같은 규칙이라 일관된다.
- **B**: 삭제 없이 항상 비활성만. 구현이 단순하고 이력이 남지만 **이름이 계속 점유**돼 같은 이름을 다시 못 쓴다(UNIQUE가 비활성 행 포함).
- 어느 쪽이든 **비활성 이름 점유** 문제는 남는다: 비활성 하부 업무와 같은 이름의 새 하부 업무는 `CreatePackage` 에서 「같은 이름의 하부 업무가 있습니다」로 막힌다. 비활성 목록을 화면에 보이고 「되돌리기」를 주면 사용자가 이유를 알 수 있다(§8-1).
- 실적 판단의 「일 이벤트」는 계획 삭제처럼 `status IN ('done','in_progress')` 만으로는 부족하다. 사이트 완료 후 취소한 이벤트나 수량 기록(음수 보정)이 `package_events` 에만 남을 수 있어서 **`package_events` 행 존재 여부를 실적 기준에 넣는 걸 권한다.**

## 7. 「변경 내용 저장」(C-2) 한 트랜잭션 가능성

**현재 구조**
- `UpdatePhaseExt`, `UpdatePackageMeta`, `UpdatePlan` 은 **각자 `r.db.Begin()` 으로 자기 트랜잭션을 연다**. `*sql.Tx` 를 받는 변형은 없다.
- 마감 변경 이력 헬퍼 `recordEndChangeTx(tx, …)` 는 **이미 tx 를 받는다**(세 함수가 같은 헬퍼를 쓴다) → 이력은 같은 트랜잭션에 넣을 수 있다.
- 감사 로그는 핸들러에서 커밋 **뒤에** `audit.LogWithReason`(별도 호출, 실패해도 변경은 유지)으로 남긴다. 같은 트랜잭션에 넣는 `audit.InsertTx` 가 이미 있어 쓸 수 있다.
- DB 연결 풀은 `MaxOpenConns(8)`, `busy_timeout 5000ms`. 배치 트랜잭션이 열려 있는 동안 다른 `r.db` 쓰기를 호출하면 같은 데이터에 잠금 대기가 생기므로, **배치 안에서는 전부 tx 변형만** 써야 한다.

**필요한 변경 범위(추정)**
1. 위 세 함수를 `…Tx(tx, …)` 본체 + 기존 이름 래퍼로 쪼갠다(래퍼는 `Begin` → 본체 → `Commit`). 기존 호출·시험은 그대로 유지.
2. 신규 하부 업무 수정(이름·유형·다음 할 일·상태·순서·삭제)도 처음부터 tx 변형으로 만든다.
3. 핸들러 `POST /projects/:id/structure/batch`: 폼 묶음(항목 종류·ID·필드)을 받아 순서대로 tx 변형 호출 → 하나라도 실패하면 롤백하고 실패 항목·사유를 되돌려 준다. 감사 로그는 `InsertTx`.
4. 권한은 항목마다 다르다(1단계·하부 업무는 설계 권한자, 계획은 계획 권한자). 배치 핸들러가 항목별로 `CanEditPhase`/`CanManagePlans` 를 다시 검사해야 한다.
5. 실패 항목 표시·입력값 유지·열린 접힘 유지는 화면 쪽 작업(95-163 입력값 유지 규칙 재사용).

**평가**: 가능하다. 대신 저장소 함수 3개를 수정하는 리팩터링이라 회귀 시험(95-120P·95-175·95-176·95-179·95-180)을 같이 돌려야 한다. **차선책**(폼 하나씩 순차 저장, 실패에서 멈춤)은 저장소를 건드리지 않아 빠르지만, 도중 실패 시 「일부만 저장된 상태」가 남는다.

## 8. 지시서에 없던 걸림돌 (구현 전에 알아야 할 것)

1. **비활성 하부 업무는 지금 화면에서 사라진다.** 트리 조회가 `is_active=1` 만 읽어서(`project_structure_tree.go:199`, 가벼운 트리 `:456`·`package_progress.go:631`) 지시서 §4 A-7 의 「비활성은 목록 아래 접힘으로 보인다」를 하려면 **비활성을 읽는 조회와 노드 필드가 새로 필요**하다. 1단계는 `is_active` 폼 값을 hidden 으로 들고 다니며 비활성도 목록에 보인다(투명 표시)는 점이 다르다.
2. **하부 업무 「보류」는 작업 등록 선택에 영향이 없다.** `SetTaskPlanLink` 는 보류 **계획**만 거부하고 하부 업무 상태는 안 본다. 수량만 하부 업무의 선택지(`PlanOption`)에도 `Hold`/`Done` 플래그가 안 채워져 `plan-sites.js` 의 `o.Hold`·`o.Done` 판정이 걸리지 않는다. 「보류」를 의미 있게 하려면 이 두 곳을 같이 고쳐야 한다(지시서 기본안은 「칩만 보류 표시, 분모 그대로」라 이쪽이 범위인지 질문 5와 함께 확인 필요).
3. **대시보드·주간 보고서·업무 회의의 진행 줄(`lightTrees`)은 하부 업무 상태를 무시한다.** 쿼리는 `pk.status` 를 읽지만 `buildPkg` 에 `"auto"` 를 하드코딩해 넘긴다(`package_progress.go:743`). 수행 구조 화면에서 「완료」로 확정해도 이 세 화면의 단계 표시(`진행 중`)에는 반영되지 않는다.
4. **이름 비교 기준이 곳곳에서 다르다**(§5 표). 특히 사업 통합만 정확 비교.
5. **저장 후 위치**(§9)와 **접힘 상태** 유지가 지금은 없다.

## 9. 저장 후 같은 위치로 돌아오는가 (`phaseRedirect`)

- 모든 저장은 `/projects/ID?ok=…#project-phases` 로 돌아간다(`phaseRedirect`). **단계·하부 업무·계획 단위 앵커는 없다.** 렌더 HTML에 `id="phase-…"`·`id="package-…"` 가 **없고** `data-phase-id`·`data-package-id` 속성만 있다(앵커로 못 쓴다).
- 결과: 구조가 길면 저장 때마다 「수행 구조」 섹션 맨 위로 튄다. 지시서 §4 A-1 의 「해당 하부 업무 위치로 스크롤」은 **`id` 앵커와 리다이렉트 해시 추가가 필요**하다.
- 「일자·배지 수정」 `<details>` 는 서버가 열린 상태를 저장하지 않는다. 저장 뒤에는 다시 접힌다. `#project-phases` 섹션 자체는 `PhaseOpen`(사업 유형 기준)으로 열린다. 이 상태를 기억하는 JS는 없다(`data-phase-tab` 사용처 검색 0건).
- 1단계 폼은 `<details>` 가 아니라 **항상 펼쳐진** 폼이라 단계가 여러 개면 하부 업무 줄이 아래로 밀린다(사용자 화면과 같은 현상). 지시서 §4 C 의 「1단계도 접힘으로」가 이 문제에 직접 답한다.

## 11. 확인이 필요한 결정
지시서 §7 의 6건 + 이번에 새로 생긴 것.

1. (기존 1) 하부 업무를 다른 단위 업무로 옮기는 기능은 이번 제외.
2. (기존 2) 유형 변경은 실적이 없을 때만.
3. (기존 3) 삭제는 실적이 없을 때만, 있으면 비활성. **실적 기준에 `package_events` 행 존재를 넣는 것(§6)에 동의하는지.**
4. (기존 4) 수행 담당은 계획만 수정. 현재 동작과 같다(§2).
5. (기존 5) 「보류」 상태를 둔다. **보류를 둘 때 작업 등록 선택에서 막을지(§8-2), 대시보드·주간·회의 진행 줄에도 반영할지(§8-3)** 함께 정해야 한다.
6. (기존 6) 변경 내용 저장: 한 트랜잭션 기본안. §7 에서 가능함을 확인했고 저장소 함수 3개 리팩터링이 필요하다.
7. **(신규)** 사업 통합의 하부 업무 이름 비교를 정규화로 맞출지(이번 범위에 넣을지, 별도로 둘지).
8. **(신규)** 비활성 하부 업무 이름 점유: 같은 이름 새 하부 업무를 막고 「비활성 목록에 있습니다, 되돌리기」로 안내하는 것(기본안)으로 갈지, 비활성 이름은 자동으로 바꿔(예: 「이름(비활성)」) 풀어줄지.
9. **(신규)** 계획 사이트 수정 화면(§3)은 지시서 B-2 전체(검색 선택·추가·제외·이동·목표 수량·같은 수량 적용)를 이번에 다 할지, 먼저 「추가·제외·이동」만 하고 수량 입력은 뒤로 미룰지.

확인해 주시면 §4 A·B·C·C-2 를 구현한다(결정 1~6 은 기본안, 7~9 는 답에 따라).
