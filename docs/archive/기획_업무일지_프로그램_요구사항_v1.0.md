## 1. 추진 배경 및 목표

본 시스템은 고객기관의 기본 정보와 담당자, 설치자산, 수행관계, 지원이력을 표준화하여 AS 접수·처리·현황 관리를 체계화하기 위한 고객지원 시스템이다.

특히 고객기관 내 설치 장비의 상당수가 타사 납품 또는 과거 설치 자산인 현실을 반영하여, 당사 계약 유무와 무관하게 기관 전체 설치환경을 관리하고 향후 교체 시점에 영업 기회를 발굴할 수 있도록 설계한다.

### 1.1 추진 배경

- 고객기관의 장비·시스템은 다수의 제조사, 협력사, 과거 설치업체가 혼재되어 있어 현장 정보가 분산됨.
- 담당자 교체가 잦아 현재 담당자만 관리하면 업무 이력과 대응 맥락이 단절됨.
- AS 접수 시 설치 위치, 제품 정보, 설치환경, 요청 주체를 즉시 확인할 수 있는 기준정보가 필요함.
- 타사 설치 장비라도 교체주기, 노후도, 장애 빈도를 파악하면 향후 교체 영업과 제안 활동으로 연결 가능함.

### 1.2 시스템 목표

- 고객기관/공간/담당자/설치자산 정보를 일관된 구조로 축적한다.
- AS 접수부터 처리 완료, 후속조치까지 전 과정을 이력으로 남긴다.
- 현재 운영 자산과 과거 이력을 함께 관리하여 장애 대응 정확도를 높인다.
- 노후장비, 장애다발장비, 지원빈도 높은 기관을 식별하여 교체 및 업그레이드 영업에 활용한다.

## 2. 시스템 성격과 기본 원칙

### 2.1 시스템 정의

본 시스템은 일반적인 계약관리형 CRM이 아니라, 기관 중심의 운영형 고객지원 시스템이다. 핵심 관리 축은 기관 기준정보, 공간정보, 담당자 및 이력, 설치자산, 수행관계, AS 운영정보이다.

### 2.2 설계 원칙

- 계약 여부와 무관하게 고객기관 내 운영대상 자산을 관리한다.
- 모든 주요 엔터티는 이름이 아닌 고유 ID로 연결한다.
- 현재 정보와 이력 정보를 분리하여 변경 추적이 가능하도록 한다.
- 설치 위치는 자유입력 최소화, 건물-층-실 구조 기반으로 표준화한다.
- AS 정보는 설치자산과 연결하여 동일 장비의 반복 장애와 교체주기를 추적한다.
- 비밀번호 등 민감정보는 평문 저장을 지양하고 암호화 파일 또는 별도 금고 체계와 연결한다.

### 5.1 고객 마스터

| 기본 | 고객ID | 내부 고유 식별자 | Y |

| 분류 | 업종 | 도서관, 학교, 공공기관 등 | Y |

| 관리 | 사용여부/비고 | 통합, 폐쇄, 휴면 등 관리 | Y |
| 관리 | **확인 필요 표식 / 사유** | 사람이 손으로 확인·보정해야 하는 기관 표시 | N |

**확인 필요 표식** — 외부 데이터를 넣다가 **기존 고객과 매칭되지 않아 자동 생성된 기관**은 `확인 필요` 표식과 사유가 붙는다.

- 고객현황 상단에 **「확인 필요 N건 보기」** 필터, 목록 기관명 옆에 **확인 필요** 뱃지(사유는 툴팁)
- 고객 상세 상단에 사유 배너 + **정보 수정 / 확인 완료** 버튼
- 사람이 보정을 마치고 **확인 완료**를 누르면 표식과 사유가 함께 지워진다. 반대로 상세에서 임의의 기관을 **확인 필요로 표시**할 수도 있다.
- 고객 정보를 수정해도 표식은 유지된다(명시적으로 해제해야 사라진다). 표식 자동 부여는 **최초 1회만** 수행하므로, 해제한 기관이 다시 표시되지 않는다.
- 권한: 기준정보 쓰기 권한(관리자·접수담당)

### 5.4 담당자 이력 관리

- 현재 담당자 정보는 최신값만 유지하고, **담당자가 바뀐 경우**(전보·퇴직·업무조정) 과거 구간은 별도 이력 행으로 보존한다.
- 단순 연락처 수정 등 **정보 수정 로그는 이력 목록에 올리지 않는다.**
- 기관 이동(전보), 퇴임(퇴직), 주·부·일반 담당 구분 변경(업무조정)은 부임일/퇴임일 기준으로 관리한다.
- 특정 AS 건이 발생한 시점의 실제 담당자를 재현할 수 있어야 한다.
- **담당자 이력 화면(§13):** 기관(사이트)별 **담당자 변경 이력**을 조회한다. 목록 컬럼은 **이름 · 소속(소속기관/통합사업자/협력업체/기타) · 부임일 · 퇴임일 · 담당구분 · 변경사유 · 전화번호 · 핸드폰 · 이메일**. 아직 담당자가 바뀌지 않았다면 **현행 담당자 정보만**(보통 1명) 리스트로 표시한다. 기관·담당자 콤보로 필터할 수 있다.

| 항목 | 설명 |
|------|------|
| 담당자이력ID | 이력 고유 식별자 |
| 담당자ID / 고객ID | 해당 담당자와 기관 연결 |
| 부임일 / 퇴임일 | 해당 구간 유효기간 |
| 소속 | 소속기관 / 통합사업자 / 협력업체 / 기타 |
| 담당구분 | 주담당 / 부담당 / 일반 담당자 |
| 연락처 / 핸드폰 / 이메일 | 해당 기간의 연락정보 |
| 변경사유 | **전보 / 퇴직 / 업무조정** |
| 등록일 / 등록자 | 입력 추적용 |

| 담당 | 고객담당자ID / 당사담당자ID | 현행 담당 연결 |
| 위치 | 건물ID / 층ID / 실ID / **설치위치** / 상세위치 | 자산 폼의 **공간정보**는 읽기전용(없으면 `-`). **공간관리 추가/연동**으로만 변경. 연동 선택 시 건물·층·호 콤보 표시. **설치위치**는 공간정보(건물 층 호, 띄어쓰기)를 반영해 입력·AS 표시 |

#### 유지보수 계약 항목(설치자산)

현업 유지보수현황(유/무상·점검주기·청구처)을 반영한다. **관리유형**(직접유지보수·장애대응·**타사장비** 등)과 혼동하지 않는다.

#### 타사 장비

기관 현장에는 당사 계약 밖 타사 장비가 함께 있는 경우가 많다. 기록은 하되 **장비 자체를 당사가 관리하지 않는다.**

- **관리유형 `타사장비`:** 타사 장비임을 구분하는 값. 현재관리대상여부는 **아니오**.
- **사업(프로젝트):** 타사 장비는 사업에 **넣지 않는 것이 기본**. 자산 등록 시 사업을 자동으로 넣지 않으며, 사용자가 선택한 경우만 연결한다.
- **연관 선택:** 당사 관리 제품과 연동되어 현장 파악이 필요할 때만 사업을 선택(연결)할 수 있다. 예: KLAS는 타사 게이트·무인대출기와 연동되어 운영되는 경우가 많다. 이 경우에도 유지보수 대상은 KLAS이며 타사 장비 자체는 관리하지 않는다.
- **설치주체와 구분:** 설치주체 `타사`는 누가 납품·설치했는지만 나타낸다. 타사 납품이어도 당사가 유지보수하면 `직접유지보수` 등을 쓴다.

## 8. AS 접수·처리·현황 관리 설계

### 단계별 처리

| 단계 | 핵심 처리 | 주요 입력/출력 |
|------|-----------|----------------|
| 1. 접수 | 기관·설치자산 식별, 증상 등록 | 접수번호, 고객, 설치ID, 요청내용, 긴급도 |
| 2. 분류 | 장애유형, 제품구분, 요청주체, 담당 배정 | 담당자, SLA, 처리우선순위 |
| 3. 처리 | 원인분석, 현장/원격조치, 부품교체, 협력사 연계 | 처리내역, 원인, 사용부품 |
| 4. 완료 | 조치결과 확인 및 완료처리 | 완료일시, 결과코드, 고객확인 |
| 5. 후속 | 재발방지, 교체검토, 영업전환 | 후속조치, 교체대상 여부, 영업메모 |

### 접수 Case와 조치 이력 (원칙)

접수 1건은 **하나의 업무 Case**다. 한 번의 조치로 끝나지 않아도 **새 접수로 나누지 않는다.** 재방문·추가조치·대기(보류)·이관은 같은 접수번호 아래 **조치 이력을 누적**한다.

```text
접수 → 1차 조치 → (부품 부족·이관·대기) → 2차 조치 → 완료
         └ 전부 동일 접수번호 · Timeline으로 조회
```

**엔티티는 신설하지 않는다.** 설계 개념(접수 Case / 현재 상태 / 조치 이력)은 아래 기존 테이블에 대응한다.

| 개념 | 테이블 | 역할 |
|------|--------|------|
| 접수 Case · 현재 상태 | `as_receipts` | 접수번호, 증상, **현재** 상태·담당자·결과코드 |
| 조치 이력 | `as_processes` | 1:N. Timeline. **각 회차의** 조치내용·결과·다음일정·이관/대기 사유 |
| 다음 일정 | `as_work_items` | `[확인]` · `[재방문]` (`{접수번호}-Wnn`) |
| 관리자 수정 이력 | `data_change_logs` | 변경 전·후 JSON. 완료 건 잠금 해제는 `as_edit_unlocks` |

**화면 분리를 유지한다.** 접수 상세(`/as/{id}`)에는 접수 내용만 둔다. Timeline·조치 추가는 **조치 화면**(`/as/{id}/action`)에 둔다. 일일 업무 등록(시간표) → 조치 동선은 바꾸지 않는다.

**이력은 덮어쓰지 않고 추가한다.** 일반 사용자는 과거 접수·조치 내용을 수정·삭제하지 못하고, **새 조치만** 등록한다. 접수의 `result_code`·상태는 **마지막 조치 결과로 갱신**하되, 이전 회차의 결과·사유·예정일은 `as_processes` 각 행에 남겨 Timeline에서 그대로 본다.

**완료 건을 같은 접수번호로 다시 여는 재오픈은 하지 않는다.** 오기재는 관리자 잠금 해제 후 수정(이력 필수). 완료 후 **같은 증상이 다시 나오면 재접수**(새 번호, 원 건 연결). 둘을 섞지 않는다.

**삭제는 원칙적으로 일반 사용자에게 제공하지 않는다.** 오접수는 **접수취소**. 테스트·중복 등 삭제는 **관리자만**(접수 삭제 시 처리 기록·하부업무 함께 삭제).

| 고객확인자 / 확인일시 | 완료 확인 | 조치 시 **기관 담당자 콤보+직접입력** |
| 후속조치 | 정기점검, 교체제안, 교육안내 등 | |

**조치 결과 (화면 문구 → 저장 코드).** 조치 등록 화면의 결과는 아래 다섯 가지로 고른다. 선택에 따라 추가 입력(재방문·이관·대기)을 보여 준다. **저장 코드·상태·통계 규칙은 바꾸지 않는다.**

| 화면 문구 | 저장 결과코드 | 접수 상태 | 다음에 생기는 것 |
|-----------|---------------|-----------|------------------|
| 완료 | `done` | 완료 | — |
| 추가조치 필요 | `partial` | 부분완료 | 방문예정일 필수 · `[재방문]` |
| 재방문 필요 | `revisit_needed` | 부분완료 | 방문예정일 필수 · `[재방문]` · 재방문 사유·준비사항(선택) |
| 이관 · 처리 확인 후 완료 | `transfer` + `completed` | 완료 | — |
| 이관 · 우리 팀 추가 작업 | `transfer` + `waiting` | 부분완료 | 확인예정일·대상자·연락처 필수 · `[확인]` · 이후 필요 시 `[재방문]` |
| 대기 | 보류(`hold`) | 보류 | 대기 사유·후속(조치/이관/접수취소) 필수. 확인 예정일 |

이관 화면의 「이관 후 처리」는 위 두 줄이다. 코드명 `TRANSFER_CONFIRM_ONLY` / `TRANSFER_RETURN_REQUIRED` 를 새로 만들지 않고 `transfer_detail` = `completed` / `waiting` 을 쓴다.

**조치 결과코드 → 상태·일정 (필수):**

| 결과코드 | 상태 | 필수·동작 |
|----------|------|-----------|
| 완료(`done`) | **완료** | 완료일시(없으면 저장 시각). 통계·운영 모두 완료. 일반 사용자는 추가 조치 불가 |
| 부분완료(`partial`) | **부분완료** | 추가 업무가 남은 경우(화면 **추가조치 필요**). **방문예정일자** 필수·하부업무 `[재방문]`. **완료일시 기록(통계=완료)**, 목록·일일업무·미완료는 **진행중**으로 관리 |
| 타사이관(`transfer`) · 세부=완료(`completed`) | **완료** | 화면 **처리 확인 후 완료**. 이관 결과까지 끝나 접수를 완료 |
| 타사이관(`transfer`) · 세부=조치결과대기(`waiting`) | **부분완료** | 화면 **우리 팀 추가 작업**. **확인예정일자·확인대상자·연락처** 필수. 하부업무 `[확인]`(`{접수}-Wnn`) 생성. **일자확정** 체크 시 해당일 업무로 확정(부모 예정업무일 동기). 완료일시 기록(통계=완료). 결과 미수신 시 다음 확인예정일 입력·재등록. 결과 수신 후 **재방문 일정**+일자확정 → `[재방문]` 하부업무 |
| 재방문필요(`revisit_needed`) | **부분완료** | 화면 **재방문 필요**. **방문예정일자** 필수. 하부업무 `[재방문]` 생성. **일정확정** 시 일정 확정. 완료일시 기록(통계=완료), 운영은 진행중 |

- **AS 목록:** 접수번호 행 다음에 하부업무를 **들여쓰기**로 표시(`[확인]`/`[재방문]` · 번호 · 예정일 · 확정여부). 클릭 시 부모 접수 상세로 이동.
- **삭제:** AS 접수·처리 기록 삭제는 **관리자만** 가능하다. 접수 삭제 시 처리 기록·하부업무도 함께 삭제된다. 일반 사용자에게 삭제 버튼을 두지 않는다.
- **완료·종료 읽기 전용:** `completed`·`closed` 건은 기본 **조회만** 가능하다. 접수·조치·삭제·첨부 변경 불가. **같은 번호로 재오픈하지 않는다.** **재접수**만 허용(새 접수 생성).
- **관리자 수정 잠금 해제:** 관리자만 「수정」 버튼이 보인다. **로그인 비밀번호와 다른** 수정 전용 비밀번호(`app_settings.as_completed_edit_password_hash`, 기본 `as-edit`, `/users`에서 변경)를 입력하면 해당 건에 대해 **30분** 잠금 해제(`as_edit_unlocks`). 시도는 `as_edit_unlock_log`에 남긴다. 잠금 해제 전에는 수정 API도 거부한다. 수정 시 `data_change_logs`에 수정 대상·전·후·수정자·일시·사유를 남긴다.
- **처리 이력(Timeline):** 조치 화면(`/as/{id}/action`)에 **시간순 Timeline**으로 표시한다. 각 `as_processes` 행에 조치일시·조치자·내용뿐 아니라 **조치결과·다음 작업 예정일·대기/이관 사유**를 저장해, 접수의 현재 결과코드가 바뀌어도 1차·2차 이력이 남는다. **장비 AS 내역**은 접수 상세에서 팝업 조회(현재 건 제외). 접수 폼의 기관별 과거 완료 AS 리스트는 별도 유지.
- **접수 상세(`/as/{id}`):** **접수 내용만** 표시(기본·기기 정보). 조치·처리이력·첨부·하부업무·워크플로 콤보는 두지 않는다. Timeline·[조치 추가]를 접수 상세에 합치지 않는다. **일일 업무 등록** 버튼으로 일일 업무(고유번호)를 만들고, 이미 있으면 **일일 업무**로 업무 화면으로 이동한다.
- **일일 업무 → 조치:** 시간표 **조치** 버튼·업무 화면의 **조치** → 조치 전용 화면(`/as/{id}/action`). 조치 화면에는 조치·**근무구분(내근/외근)**·결과(위 다섯 가지)·첨부·하부업무·처리이력 Timeline·보류(대기)/이관/취소만 둔다. **접수 보기**는 iframe. **완료·종료** 건은 일일 업무 화면에 **조치 완료** 요약을 보인다.
- **AS 조치 첨부:** 조치완료보고서·관련 파일. 서버 폴더 `data/uploads/as/{접수ID}/`에 저장하고, DB(`attachments`)에는 **원본 파일명**과 **저장 경로(링크)**만 둔다. 화면에는 **파일명만** 표시(미리보기 없음). 이름 클릭 시 다운로드.
- **보류(화면 「대기」):** 작업을 포기한 것이 아니라 부품·고객 일정·개발 수정 등 **조건을 기다리는** 상태다. 코드·URL은 `hold`를 유지한다(`/as?status=hold`). 선택 시 콤보로 **조치 / 이관 / 접수취소**를 고른 뒤 대기 사유를 입력한다. 목록·상세의 **삭제(보류 삭제)** 는 접수를 지우지 않고 **접수 상태**로 되돌린다.
- **이관:** 조치 결과에서 이관을 고르면 「처리 확인 후 완료」와 「우리 팀 추가 작업」을 반드시 고른다. 목록 `/as?status=transfer`(이관·회신 대기), `/as?status=transfer_overdue`(회신확인일 경과). 확인 후 완료는 처리결과+완료일. **담당자 미완료(`open`)** 에 이관·보류를 포함한다. 이관을 진행중·보류와 합치지 않는다. 이관 중 표시 상태 코드 `transfer`는 유지하되, **조치 결과 대기(우리 팀 후속)** 는 저장 상태가 **부분완료**이다.
- **접수취소:** 접수취소 목록(`/as?status=cancelled`)에서 관리. 취소일 기본=당일(수정 가능).

**동일 증상 재접수** — 조치를 마쳐 완료한 뒤에도 **같은 증상이 다시 나오는 일**이 있다. 이때 끝난 건을 되살리지(재오픈하지) 않고 **새 접수**를 만들어 둘을 이어 둔다. 완료 이력이 그대로 남아야 재발 횟수를 셀 수 있기 때문이다.

| 항목 | 규칙 |
|------|------|
| 대상 | **완료·종료** 건만. 진행중·부분완료·보류·이관은 재접수 대신 **같은 접수의 조치**(재방문·추가조치)로 이어간다 |
| 결과 | **새 접수번호**(`R{YYMM}-{NNN}`)를 받는다. 원 건의 상태·완료일시는 그대로 둔다 |
| 승계 | 기관·자산·요청자·**증상**·긴급도·담당자를 그대로 가져오고, 화면에서 고칠 수 있다 |
| 입력 | **재접수 사유 필수**. 접수채널·증상·긴급도·담당자·방문예정일(일정확정)은 선택 |
| 표시 | 재접수 건 상세·조치 상단에 **원 완료 건(1차)** 카드(접수번호·완료일시·조치내용·링크), 재접수 사유. 원 건 상세에는 **재접수 목록**. 목록에는 **재접수** 뱃지 |
| 이력 | 원 건에 「동일 증상 재접수 — {새 접수번호} (사유: …)」 처리 이력이 남는다 |
| 권한 | 접수 권한(관리자·접수담당) |
- **미완료 업무:** `received`·`assigned`·`in_progress`·`partial_complete`·`hold`·`transfer`. 대시보드에 **이관 대기**(확인일 경과 건 강조)·보류(대기) 요약 리스트를 표시한다.
- **부분완료:** 추가 업무·이관(우리 팀 후속)·재방문필요 시 사용. **저장 상태·통계는 `partial_complete`(부분완료)를 유지**한다. 운영 의미는 「재조치예정」이다. 화면 상태 뱃지는 **「부분완료」** 를 쓰고, 맥락(재방문 / 확인 대기)은 하부업무로 구분한다. **부모 접수는 통계 완료**에 포함하고, 그때 생성된 **하위업무(확인·재방문)는 통계 접수·미완료(진행중)** 로 별도 집계한다. 운영(목록·일일업무)에서는 진행중으로 관리. 완료·종료와 달리 읽기 전용이 아니며 재접수 대상이 아니다. 재조치예정 상태를 새로 만들지 않는다.

### 통계 (§13)

모든 통계는 **관리 단위**로 집계한다. 관리 단위 = **기간**(일별 / 주별 / 월별 / **사용자 지정 기간**) × **담당**(팀전체 / 담당자별) × **사업**(사업명, 선택 시). 업무별(제품) 필터는 병행.

| 구분 | 내용 |
|------|------|
| 메뉴 | `/stats` — **KPI·업무분석·그래프·기간 요약**. `/stats/detail` — 상세·엑셀 |
| 사업팀 관리 목표 | **계획대비 실행율 90% 이상** · **접수→방문(조치시작) 평균 3일 이내** · **접수→조치완료 평균 7일(1주일) 이내**. 목표 대비 기준충족/미충족 · 이전 기간 대비 증감. 대시보드 주간 KPI와 **동일 식** |
| 통계 대상 | **팀전체 / 담당자별 / 업무별**(앤로보틱스·KLAS·세종 K-LAS) · **사업별**(프로젝트). 1항 목표값도 이 필터로 다시 계산 |
| 통계 기간 | **일별 / 주별 / 월별 / 기간 사용자 선택** |
| 표시 형태 | **숫자(KPI 카드)** · **업무 분석** · **막대 그래프**(일자별 접수·조치중·완료) · **선 그래프**(실행률 추이) · **전·현·다음** 표 |
| 요약 표 | **예정업무 / 접수 / 처리** · **계획수정** · **계획대비 실행률(%)** 을 AS·정기점검·행정/지원으로 표시 |

| 일일 | 열 = **전일 / 오늘 / 익일** · 차트 = 최근 14일 |
| 주간 | 열 = **전주 / 금주 / 차주** (월~일) · 차트 = 전전주·전주·이번주 |
| 월간 | 열 = **전월 / 당월 / 익월** · 차트 = 전전월·전월·이번달 |
| 기간 지정 | 시작일~종료일(포함). 차트는 구간 길이에 따라 일/주/월 버킷 |
| 예정 기준 | AS=방문예정일 · 정기점검=방문일(예약) · 행정/지원=배정일(없으면 예정일) |
| 접수 기준 | AS=접수일시 · **정기점검=그 기간에 방문 예약된 건(`visit_date`)** · 행정/지원=예정과 동일 취급 |

| 정기점검 월 목표 | 점검 사이트 설정의 **점검주기**(월/홀수격월/짝수격월/분기/반기/년1회)로 그 달에 도래하는 사이트 × 점검대상(KLAS 1 + RFID 1). 둘 다 미지정이면 1건. **별도 집계 테이블 없이** `maintenance_site_config`·`maintenance_visits`로 산출 |
| 정기점검 누적·남은 | **누적** = 그 달 1일 ~ 해당 열(일·주·월) 종료일까지 조치 완료 건. **남은** = 월 목표 − 누적(0 미만이면 0). 주가 월을 걸치면 **기간 시작일(월요일)이 속한 달**을 월 목표로 한다 |
| 정기점검 예정 표시 | 일·주·월 모두 예정 칸에 **그 기간 방문 예약 건수**. **주간(및 일간)** 예정 칸에는 이어서 **`(누적건수/남은건수)`** 를 붙인다. 예: 월 목표 75, 8월 1주 10곳 완료 → 예정 `10 (10/65)`, 8월 2주 11곳 완료 → `11 (21/54)` |
| 계획수정 | 예정일과 완료일(또는 배정일)이 다른 건 — 계획대로 갔는지 여부 파악용 |
| 실행률 | **계획대로 완료÷예정×100** (예정일 당일 완료 건 / 예정적). 일정 변경(계획수정)된 건은 분자에서 제외 → 예: 예정 4곳 중 2곳 변경이면 **50%**. 처리 건수와 별개이며 **100% 초과 없음**. 지난 일은 `daily_meeting_stats`에 저장 |
| 업무 분석 | **AS + 정기점검 + 행정/지원** 합산. 선택 기간의 **접수 · 방문(조치시작) · 완료 · 업무 이관(이월)** 을 유형별로도 표시. 이관=상태「이관」이 아니라 **이전 기간에서 미완료로 넘어온 수(Carry-in)** 와 **기간 종료 시 다음으로 넘긴 수(Carry-out)** |
| 일자 목록 | 관리 단위 기간에 걸친 건의 **접수일 / 방문(조치시작)일 / 조치완료일**(AS·정기점검·행정) |
| 최장 소요 | 기간 내 소요시간(AS 처리이력 `time_spent` 합, 없으면 조치시작→완료 · 행정/점검은 배정 소요분). **건수 기준** 표시 건수: 기간 접수 10건 미만=**1건**, 10건 이상=**2건**, 20건 이상=**3건**. **시간 기준**: 소요 **1시간 초과** 건 목록 |
| 방문 차수 | AS 처리이력(`as_processes`) 건수(없으면 조치시작 있으면 1차). 정기점검은 방문 1차. **1차 이상**인 건을 차수 많은 순으로 표시 |
| 긴급·중요 상 | **긴급도=상 그리고 중요도=상** 인 AS 건(기간에 접쳤거나 접수·완료된 건) |
| 주간업무보고서 | `/stats/weekly-report.xlsx` 엑셀. 시트 **통계**(상단 **담당자 드롭다운**(전체·담당자명)으로 선택하면 해당 담당자의 전전주·전주·이번주 × 합계/AS/정기점검/행정 · 접수/방문/완료 건수 + 실행율·방문일수(3일)·완료일수(7일)). **정기점검 월 진행** 표를 같은 시트에 둔다: 주별 **월목표 · 접수(예약) · 방문(완료) · 누적 · 남은**. 담당자 드롭다운에 맞춰 바뀐다. 시트 **업무리스트**(해당 3주 업무, 엑셀 필터: 접수일·처리일·사이트명·처리담당자·처리내용·처리결과), 시트 **진행중건**(아직 처리되지 않은 전 건) |
| 상세 통계 | **건수 통계** + 상세 리스트 · 엑셀. 종류: 업무진행/완료/접수/지연. 범위: 팀전체·담당자별. 기간: 일·주·월·분기·기간지정 |
| 집계 기준일(상세) | 접수업무·지연·업무진행 → **접수일시**. 완료업무 → **완료일시**. 지연 = 미완료이면서 `접수일+3일` 초과 |
| 상세 열 | 제품분류, 제품모델명, 업무형태, 접수형태, 거래처명, 수행담당자, 접수내용, 처리내용, 처리상태 |
| 엑셀 | 상세 화면·요약 화면에서 선택한 통계종류·기간·범위 기준 |

### 10.1 역할별 대시보드

홈(대시보드)은 **로그인한 사용자 역할**에 따라 업무 요약을 보여 준다. 기술담당은 **본인 배정**, 관리자·접수담당은 **전체**(단, 담당자 미배정은 항상 전체). 카드·숫자를 누르면 `/work?bucket=…` 통합 업무 리스트로 이동한다.

**상단(표시 전용, 세로 압축):** **주간 통계** KPI 3종(계획대비 실행률 **90%** · 접수→방문 **3일** · 접수→조치완료 **7일**). 팀전체·금주 기준. `/stats?view=week`와 동일 식. 필터·편집 없음.

**KPI 카드:** 아래 6개를 **한 줄**(넓은 화면 기준)로 나열한다.

| 카드 | 내용 |
|------|------|
| 전체 업무 | 진행중·미완료 업무 건수 |
| 오늘 예정 업무 | 오늘 확정 예정일 업무. **접두어별 건수**(AS·확인·정기점검·일반) |
| 지연 업무 | 확정 예정일이 지났는데 미완료 **· 아직 다녀오지 않은 건만** |
| 오늘 완료 | 오늘 완료 건. **접두어별 건수** |
| 방문 미확정 | 담당자 배정됐으나 **일정 미확정**, 또는 **다녀왔지만 다음 일정을 안 잡은 건** |
| 담당자 미배정 | 담당자 없는 건(**전체 대상**) |

**예정일 경과 판정** — 일정을 조정해 예정일보다 늦게(또는 이르게) 다녀오는 일이 잦다. 그래서 **예정일 당일 이후에 처리 이력이 있으면 그 예정일은 이미 소화된 것**으로 보고 지연·경과로 세지 않는다.

- 예정일이 지났고 **처리 이력 없음** → `예정일 경과`(빨강, `D+n`)
- 예정일이 지났고 **처리 이력 있음** → `다음 일정 미정`(노랑, `방문함`). 다음 방문일을 잡거나 완료 처리하면 사라진다.

**통합 업무 리스트 (`/work`):** 행마다 접두어 `[AS]` · `[정기점검]` · `[확인]` · `[일반업무]` 표시. **관리자·접수담당** 화면에서는 각 행 앞에 **담당자명**을 표기한다. 확인·재방문 하부업무·정기점검·기타업무를 AS와 함께 한 목록에서 본다.

영업·열람: 업무 대시보드 대신 「준비 중」 안내.

### 10.3 일일 업무 현황 · 칸반/목록 (워크보드)

내부 업무·프로젝트 등록·칸반·목록. 메뉴 **업무 관리 → 일일 업무 현황**(칸반·목록). 시간표 배치는 §10.4 **일일 업무 등록**.

**프로젝트(일일업무 연동):** 사업명, 발주처, 고객명, 계약방식, 청구방식, 계약기간(시작·마감), 비고, **고객 담당자**. 등록된 **사업명**은 업무 등록 시 프로젝트명 콤보에 자동 반영. **전문 관리는 §10.3.1 사업(프로젝트)관리**에서 한다.

### 10.3.1 사업(프로젝트)관리

메뉴 **사업(프로젝트)관리 → 사업(프로젝트)관리**. `/projects`

사업(계약) 마스터를 **전용 메뉴에서 CRUD**한다. 일일업무의 지원업무·통계 사업별 필터와 **동일 `work_projects`** 를 쓴다. 일일 업무 현황 모달의 프로젝트 등록은 **빠른 등록용**으로 병행 유지한다.

| 항목 | 내용 |
|------|------|
| 기본 | 사업명(필수), 짧은이름, **사업연도**, 발주처(고객 콤보+직접입력), 고객(권장·콤보), 계약·청구방식(코드 콤보+직접입력), 계약기간, 유상/무상, 색상, 상태(진행/완료/보관), 비고, 고객 담당자 |
| **범위 규칙** | 사업 1건에 규칙 N건. **상위기관**(고객 마스터) × **제품키**(klas / sejong_klas / anrobotics) × **업무유형**(as / maintenance / admin). AS는 원본에 project_id를 쓰지 않고 **규칙 매칭**으로 귀속 조회. **정기점검은 방문에 사업명(`project_id`)을 직접 둘 수 있다**(없으면 규칙 매칭) |
| 화면 | 목록(검색: 사업명·발주처·고객 / 연도·상태 필터)·등록·상세·수정. 상세에서 **보관(`archived`)/재개(`active`)**, 연결 지원업무 건수·최근 목록·일일 업무 현황 링크. 규칙·매칭 AS/정기점검/지원업무 |
| 삭제 | **관리자만**. 연결 일일업무(`work_tasks`)가 있으면 거부, 없으면 삭제 |
| 권한 | 조회·등록·수정·보관/재개: **관리자·접수담당·기술담당**. 삭제: **관리자**. 그 외 역할은 메뉴 비표시 |
| 콤보 연동 | `status=active` 사업만 일일업무 사업명 콤보에 표시(보관 시 제외) |

**예시 사업(시드):** 충남교육청 SW 유지관리(KLAS)·세종 ICT(세종 KLAS)·앤로보틱스 RFID·제천 홈페이지(준비중)·세종 무상(KLAS+RFID)·차년도 충남(행정/지원 중심).

**업무:** **업무 구분(행정업무/지원업무/AS/정기점검)**, **거래처**(기관 콤보+직접입력), 업무명, 설명, 사업명(콤보), 마감일, **소요 예상 시간(시작·종료)**, 상태(수집함/할 일/진행중/**회신 대기**/보류/이관/검토중/완료/취소 — 행정·지원. AS·점검은 원본 상태), 우선순위, 담당자(내부), 태그, 진행률

- **행정업무**: 사업명은 **선택**. 사업에 해당하는 건만 고른다. **거래처**는 주간업무보고서·통계의 사이트명(거래처)으로 쓰이며 업무명과 섞지 않는다
- **지원업무**: 사업명(프로젝트) 선택 **필수**. 거래처는 직접 지정하거나 사업의 고객을 초기값으로 쓸 수 있다
- **AS / 정기점검**: **일일 업무 등록** 모달에서 원본을 고르거나, 시간표에 배치할 때 자동 등록(아래 §10.4). 업무 구분은 각각 `AS`·`정기점검`. 등록 시 **업무 고유번호**(`work_tasks.task_id`)가 부여된다. **정기점검은 사업명(프로젝트)을 방문·업무에 지정**할 수 있다.

**하위업무(행정·지원)** — 여러 날에 걸쳐 하는 일은 **일자별 하위업무**로 나눈다.

- 상위 업무 상세(`/workboard/tasks/{id}`) 또는 등록 모달에서 **매일(기간)** 또는 **날짜 지정**으로 추가
- 하위업무마다 예정일·소요시간이 있고, 업무 등록 시간표에 따로 올린다
- 일자 하위업무(`parent_task_id`)는 **시간표 배치용**이다. GTD의 **다음 행동**과 섞지 않는다. 기존 하위업무를 다음 행동으로 자동 변환하지 않는다

### 10.3.2 행정·지원 업무 확장 (수집·다음 행동·조치 이력)

GTD의 수집→명확화→실행→검토를 **행정업무·지원업무에만** 적용한다. **AS·정기점검은 §8·§17을 따르며 이 절의 상태·엔티티를 쓰지 않는다.**

**범위 확정**

| 항목 | 규칙 |
|------|------|
| 대상 | `work_type` = `admin`(행정) · `support`(지원) 만 |
| 제외 | AS 접수·조치, 정기점검 방문. 시간표·통계 식은 유지 |
| 사업명 | 기존 `work_projects`(계약·사업 마스터). GTD의 「프로젝트」와 **이름을 섞지 않는다** |
| 복합업무 | 완료까지 행동이 2개 이상인 **행정/지원 업무 1건**. 새 `projects` 테이블을 만들지 않는다 |
| 업무번호 | 기존 `work_tasks.task_id` 유지. `WK-YYYYMM-NNNN`으로 재채번하지 않는다 |

**엔티티 (신설은 최소)**

| 개념 | 저장 | 역할 |
|------|------|------|
| 수집함 | `work_tasks.status='inbox'` | 제목만으로 빠른 등록. 아직 분류 전 |
| 업무 Case | `work_tasks` | 결과·현재 상태·담당·기한. 행정 1건 = 1 Case |
| 다음 행동 | `work_actions` (업무 1:N) | 지금 할 최소 실행. 상태: 할 일 / 진행중 / 대기 / 완료 / 취소 |
| 조치 이력 | `work_activities` (업무 1:N) | 누가 언제 무엇을 했는지. 덮어쓰지 않고 추가. AS `as_processes`와 같은 역할 |
| 회신 대기 | 다음 행동 상태 `waiting` + 대기 항목 필드 | 대상·요청내용·회신예정일·**다음 확인일** 필수 |
| 일자 하위업무 | `work_tasks.parent_task_id` | 시간표에 올리는 **그날 칸**. 다음 행동과 별개 |
| 반복 템플릿 | 2단계 (`work_recurrence_rules`) | 1단계 범위 밖 |

`tasks` / `projects` / `inbox_items` 테이블을 새로 만들어 기존 업무를 대체하지 않는다.

**상태 (업무 전체).** 저장 코드는 아래를 쓰고, 화면 문구는 괄호.

| 화면 | 코드 | 의미 |
|------|------|------|
| 수집함 | `inbox` | 미분류 |
| 할 일 | `waiting` | 시작 전·실행 예정. **지금 코드 `waiting`(대기)의 의미**. 화면만 「할 일」 |
| 진행중 | `in_progress` | 담당자가 수행 중 |
| 회신 대기 | `waiting_for` | **타인·외부의 회신·승인**을 기다림. 기존 `waiting`과 구분 |
| 보류 | `hold` | 내부 사정으로 중단. 사유·재검토일 필수 |
| 이관 | `transfer` | 기존 이관. 검토 열에 표시 |
| 검토중 | `review` | 결과물 확인·피드백. 칸반 검토 열 |
| 완료 | `complete` | 필수 다음 행동·미확인 대기가 없을 때 |
| 취소 | `cancelled` | 삭제하지 않고 보존. 사유 필수 |

**대기(할 일)와 회신 대기를 같은 말로 쓰지 않는다.** 현황 카드의 「대기」는 단계적으로 「할 일」로 바꾸고, 회신 기다림은 「회신 대기」로 둔다.

**다음 행동 vs 시간표**

- 업무는 **결과**를 관리하고, 다음 행동은 **실행**을 관리한다
- 며칠에 걸친 일도 **새 업무로 나누지 않는다.** 같은 행정 건에 다음 행동·조치 이력을 누적한다
- **오늘 시간표에 올리는 것**은 그날 실행할 **다음 행동**(예정일=그날) 또는 **일자 하위업무**다. 부모 업무 전체를 매일 복제하지 않는다
- 다음 행동이 없는 진행 중 업무는 주간 검토에서 「다음 행동 미지정」으로 경고한다

**조치 이력:** 일반 사용자는 과거 이력을 수정·삭제하지 못하고 **새 이력만** 추가한다. 유형 예: 작성·수정·검토 요청·회신·발송·독촉·완료. 관리자 수정은 `data_change_logs`.

**완료 검증:** 미완료 **필수** 다음 행동 또는 미확인 회신 대기가 있으면 일반 사용자는 완료할 수 없다. 관리자는 사유를 남기고 강제 완료할 수 있다. 완료 시 최종 조치 내용(또는 결과) 필수.

**회신 대기 전환 시 필수:** 대기 대상(내부 담당·부서·외부 업체·고객), 요청 내용, 회신 예정일 또는 **다음 확인일**.

**보류 전환 시 필수:** 사유, 재검토일.

**1단계 구현 범위 (이 절을 구현할 때):** 수집함, 상태 세분화(`inbox`·`waiting_for`·`cancelled`), 다음 행동, 조치 이력, 회신 대기·보류 필수값, 완료 검증, 오늘 할 일·기한 초과·수집함 현황. 기존 `task_id` 보존 이관.

**2단계:** 반복업무 템플릿, 문서 버전, 알림, 주간 검토 전용 화면, 댓글·참조자.

**하지 않음:** 전자결재·메일 서버 구축, 행정 상태를 AS에 적용, 사업 마스터를 GTD 프로젝트로 변경, 업무번호 재채번.

**화면 (이 절):** `/admin-work` 수집함·분류·목록, `/admin-work/stats` 현황 카드(수집함·할 일·회신 대기 구분), `/workboard/tasks/{id}` 다음 행동·조치 Timeline. 칸반·목록은 아래 §10.3 화면.

**화면:** `/workboard/kanban`(칸반), `/workboard/tasks`(목록), 모달로 프로젝트·업무 등록. 두 화면은 상단 버튼으로 서로 전환한다.

- **기준일:** 칸반·목록은 **오늘**만 표시한다. 배정일(`work_date`, 없으면 예정일 `due_date`) = 오늘.
- **칸반**: 상단에 전체·할 일·진행중·검토·완료·긴급 건수 요약. 아래는 **할 일/진행중/검토/완료 4열**. **검토 열 = 보류·이관·검토중·회신 대기**. 카드에는 업무 구분·우선순위 뱃지, 업무명, 사업명, 진행률 막대, 담당자, **D-day**를 표시한다.
- **목록**: #, 구분, 업무명, 사업명, 상태, 우선순위, 담당자, 진행률, 마감일 컬럼. 오늘 건만.
- 등록·수정은 **관리자·접수담당·기술담당**만 가능하고, 그 외 역할은 조회만 한다.

### 10.4 일일 업무 등록 (시간표 배치)

메뉴 **업무 관리 → 일일 업무 등록**. `/workboard/register?view=day|week|month&date=YYYY-MM-DD`

해야 할 업무를 오른쪽 카드 목록에서 골라 왼쪽 시간표에 **끌어다 놓아** 일정을 잡는 화면이다. 단위업무(AS·정기점검·행정·지원)는 일·주·월 시간표에 올리며, 등록 시 **업무 고유번호**가 부여된다.

**기간 단위 3종** — 상단 탭으로 전환한다.

| 뷰 | 세로축 | 가로축(열) |
|----|--------|-----------|
| **일일 업무 등록** | 07:00~20:00 · 15분 | 해당 날짜 1개 열 |
| **주간 업무 등록** | 07:00~20:00 · 15분 | 월~일 **7개 열** |
| **월간 업무 등록** | — | **일~토 캘린더 그리드**(날짜 칸에 업무 목록·미배정·더보기) |

**겹침 규칙:** 같은 담당자는 같은 날 **시간이 겹치지 않음**(일·주 동일). 자동 배정·수동 배치 모두 담당자별 빈 슬롯을 쓰며, 겹치면 거부. 다른 담당자끼리만 가로로 나란히 표시.

**「+ 일일 업무 등록」모달** — 1단계에서 종류를 고른다.

| 종류 | 입력 | 결과 |
|------|------|------|
| **행정 / 지원업무** | 거래처·업무명·설명·예정일·소요시간 등 직접 입력 | 행정·지원 업무 생성 |
| **AS 일일업무** | 미배치 AS 접수번호 검색·선택 · 예정일(선택) | AS 업무 생성 후 **AS 업무 화면**으로 이동 |
| **정기점검 일일업무** | 미배치 정기점검번호 검색·선택 · 예정일(선택) | 점검 업무 생성 후 **정기점검 업무 화면**으로 이동 |

**오른쪽 카드 3열** — 아직 시간표에 올리지 않은 업무만 표시한다.

| 열 | 출처 | 카드 표기 |
|----|------|-----------|
| **AS** | 미완료 AS 접수(아직 업무 미생성) | 업무명 `[AS]고객명_접수번호` · 접수번호(텍스트) · 증상 · 예정일 |
| **정기점검** | 정기점검 방문 계획(오늘 −7일 ~ +45일, 미생성) | 업무명 `[점검]고객_점검번호(방문일·제품)` · 점검번호(텍스트) · 설명 `[제품]고객 정기점검` · 방문예정일. **제품이 다르면 같은 날이어도 별도 카드** |
| **행정관련업무** | 시간 미지정 행정·지원·하위업무·(구현 후) 당일 다음 행동 | 업무명 · 설명 · 마감일 · 소요분. 수집함(`inbox`)은 분류 전까지 팔레트에 올리지 않거나 「수집함」으로 구분 |

**AS·정기점검 → 업무 등록 규칙**

| 항목 | AS | 정기점검 |
|------|-----|----------|
| 업무 구분 | `AS` | `정기점검` |
| 업무명 | `[AS]고객명_접수번호` | `[점검]고객명_점검번호` |
| 설명 | 접수 내용(증상) | `[점검제품]고객명 정기점검` |
| 예정일 | 방문예정일(없으면 배치일·입력일) | 방문예정일 |
| 업무 화면 | 예정일·접수내용·**AS접수이동** | 예정일·점검내용·**정기점검등록이동** |
| 원본 번호 | 접수번호·점검번호는 **텍스트 표시만**(카드에서 링크하지 않음). AS/점검은 업무 화면의 이동 버튼으로 연다 |
| 고유번호 | `work_tasks.task_id` 부여 | 동일 |

**배치 규칙**

- 카드를 **드래그해서 칸에 놓거나**, 카드를 클릭해 선택한 뒤 칸을 클릭해도 된다. **대기열(AS·정기점검)** 을 놓으면 **일일 업무 등록 모달**이 열리며 접수번호·예정일(드롭 날짜)·업무 배정일(기존 있으면 유지, 없으면 드롭 날짜)·시작·종료(기본 소요 **30분**)가 채워진다(수정 가능). **이미 배치된 카드·행정/지원 대기**는 칸에 바로 재배치된다.
- **소요 예상 시간·조치 시간**: 값은 **분 단위**로 관리한다. 시간표 **칸 표시**만 15분 단위다. 종료는 시작+소요분(기본 30분)이며 **20:00을 넘지 않는다**.
- **이미 등록된 업무** 중 **배정일(`work_date`)은 있고 시간만 비어 있는** 건 해당 날짜 **07:00부터** 자동 배치될 수 있다. `×`로 배정일을 비운 건·아직 올리지 않은 건은 대기열에 남고 자동으로 다시 올라가지 않는다.
- AS·정기점검 모달 등록 시 **업무(work_tasks)로 복사**되고 원본과 연결(`source_type`/`source_id`)된다. 같은 원본은 **한 번만** 업무로 만든다.
- **정기점검 일정 ↔ 일일 업무 동기화:** 점검 일정 화면에서 방문일·담당자·점검대상·**사업명**을 바꾸면 연결된 일일업무의 예정일·배정일·담당자·업무명·사업명도 **같은 값으로 맞춘다**. **방문 예정일을 바꾸면 그 날짜에만 1건으로 표시**하고, 미완료 일일업무도 그 날로 옮긴다. 일일 업무 등록에서 카드를 다른 날로 옮기면 점검 방문일도 따라간다. 완료된 방문의 실적일(`work_date`)은 바꾸지 않는다. 일일 업무 등록·업무처리현황 진입 시 어긋난 건을 보정한다.
- **미생성 방문:** 아직 일일업무가 없는 **미완료** 정기점검 방문은 일일 업무 등록 화면 진입 시 업무를 만들고 해당 방문일에 올린다(같은 원본 1건). `×`로 내린 뒤에는 행을 유지한 채 배정일만 비우므로 다시 자동 생성·배치하지 않는다.
- 배치된 카드의 `×`를 누르면 배정일·시간이 비워지고 오른쪽 대기열로 돌아간다. **AS·점검도 업무 행은 유지**한다(원본 연결 재사용). 행정/지원은 예정일까지 비운다.
- **버튼 클릭**: 배치된 카드의 **조치** → AS는 **조치 화면**(`/as/{id}/action`), 정기점검·행정은 **업무 화면**. **수정** → **일일 업무 수정**(`/workboard/tasks/{id}`). 조치 화면의 **접수 보기**는 iframe 팝업(닫기로 복귀). 미배치 카드의 **등록** → 등록 모달. 카드의 AS 접수번호·점검번호는 링크하지 않는다.
- **정기점검 카드 색**(팔레트·시간표 공통): 초록=앤로보틱스, 파랑=K-LAS(KLAS), 보라=세종 K-LAS. 정기점검 일정 캘린더·**업무처리현황(§10.6)** 과 동일.
- 월간 뷰에서 놓으면 그 **주에서 이번 달에 속하는 첫 날**로 배치된다.
- 상단에서 **기간 이동**(이전/다음/오늘/날짜 선택).
- **담당자 필터**: 「일일/주간/월간 업무 등록」제목 옆에 드롭다운. 기본값 **팀전체**(전원). 담당자를 고르면 시간표·오른쪽 팔레트(AS·정기점검·행정/지원)를 해당 담당자 건만 표시. 일·주·월·날짜 이동 시에도 선택 유지(`?assignee=`).
**역할:** 관리자·접수·기술담당 (등록·조회)

### 10.6 업무처리현황 (실적·예정 시간표)

메뉴 **업무 관리 → 업무처리현황**. `/work-status?view=day|week|month&date=YYYY-MM-DD&assignee=&project=&kind=action|receipt|planned`

**일일 업무 등록(§10.4)과 동일한 화면 구성**. 사업 필터 옆에 **접수 / 예정업무 / 조치** 전환. **일일 업무 회의**에서 그날 예정 건수를 볼 때 **예정업무** 탭을 쓴다.

| 항목 | 내용 |
|------|------|
| 보기 | **일일·주간·월간** 시간표(07:00~20:00 · 15분). 기본=일일 |
| 필터 | **팀전체/담당자**, **사업(프로젝트)**, **접수\|예정업무\|조치**(`kind`) |
| 조치(기본) | 기간 안 완료 실적. AS=`completed`·`closed`·`partial_complete`, 정기점검=`completed=1`, 행정/지원=`status=complete` |
| 예정업무 | 기간 안 **아직 완료되지 않은** 업무. 일일업무로 올린 건 + 아직 안 올린 AS 방문예정·정기점검 방문. 완료·종료 건은 제외 |
| 접수 | 기간 안 **신규 접수** AS(`date(receipt_datetime)`). 접수 시각을 시간표에 표시(15분 반올림, 업무시간 밖은 09:00) |
| 카드 | **조치·수정·배치 없음** — 상태 뱃지(접수/예정·진행중/완료·부분완료·방문 완료). 담당자 색은 배정자 순번 고정 팔레트 |
| 권한 | 관리자·접수·기술담당 (조회) |

### 10.5 일일 업무 회의

**메뉴 비노출.** 필요 시 URL `/meeting?date=YYYY-MM-DD` 로만 접근.

아침 회의용으로 **전일 실적 목록**과 **오늘(기준일) 예정 목록**을 한 화면에서 본다. 새 테이블 없이 기존 `/work`·통계 집계 로직을 재사용한다.

| 항목 | 내용 |
|------|------|
| 권한 | 관리자·접수·기술담당 (조회). 담당자 필터는 `/work`와 동일(기술담당 기본=본인, `mine=0`이면 팀전체) |
| 기준일 | 기본=오늘. `date`로 이동. 왼쪽=전일(`date-1`), 오른쪽=기준일 |
| 상단 요약 | 통계 일별 열(전일·오늘) 재사용 — 실행률·예정/처리 건수. `/stats?view=day`와 동일 식 |
| 전일 실적 | AS: 통계 완료 계열(`completed`·`closed`·**`partial_complete`**) + `date(COALESCE(complete_datetime, updated_at))=전일`. 정기점검: `completed=1` + `COALESCE(completed_date, visit_date)=전일`. 행정/지원: `work_tasks` `status=complete` + `date(updated_at)=전일`(완료일 컬럼 없음). 하부업무 완료·`work_other` 완료 포함 |
| 오늘 예정 | AS: 미완료 + `schedule_confirmed=1` + `visit_scheduled_date=기준일`. 정기점검: `visit_date=기준일` AND `completed=0`. 행정/지원: `work_tasks` `work_type IN (admin,support)` + `COALESCE(work_date, due_date)=기준일` + 미완료. 하부업무(`[확인]`/`[재방문]`) 일정 확정 건·`work_other` 미완료 포함 |
| 화면 | 2열 목록(유형 뱃지·기관·담당자·상태·상세 링크). 회의 의사록·출석·안건 저장은 **범위 밖** |

### 10.2 업무 고유번호 원칙

| 대상 | 포맷 | 비고 |
|------|------|------|
| 고객번호 | `C{지역코드}-{YY}-{NNN}` | 대표전화에서 지역번호 추출(없으면 `000`). 예: `C02-26-001`, `C041-26-012` |
| 설치자산 | `A{모델코드}{구분}-{NNN}` | 구분: 키오스크=1, SW=2, 키오스크외HW=3. 예: `AEZ-200E23-001` |

**모델코드 규칙(타사 장비 포함):** 자산번호는 URL 경로·이미지 파일 경로에 그대로 쓰이므로 **ASCII 영숫자와 하이픈만** 사용한다. 모델명 → 제품명 → 제조사 순으로 ASCII 문자를 찾아 대문자로 정규화하고(한글 등 비ASCII는 구분자로 처리), 셋 다 ASCII가 없으면 `ETC`를 쓴다. 예: 모델명 없이 제품명 `자료검색대`·제조사 `채움씨앤아이`만 있으면 `AETC3-001`. 타사 장비는 **모델명을 영문·숫자로 입력**하면 알아보기 쉬운 번호가 만들어진다.
| 접수번호 | `R{YYMM}-{NNN}` | 예: `R2607-001` |
| 처리번호 | `{접수번호}-P{NN}` | 예: `R2607-001-P01` |

일련은 키별 증가(고객·자산·접수는 3자리, 처리는 2자리). 기존 데이터도 동일 규칙으로 이관한다.

## 14. 핵심 업무 규칙

- 기관명과 공식명칭은 분리 관리한다.
- 사업자번호 또는 내부 중복 검증 규칙으로 동일 기관 중복 등록을 방지한다.
- 담당자는 삭제하지 않고 재직상태와 이력으로 관리한다.
- 설치자산의 위치는 건물-층-실 기준으로 선택하고, **설치위치**로 동일 층·실의 동일모델을 구분한다. 상세위치는 보조 입력이다. AS 접수 시 자산 선택 콤보에 설치위치가 함께 표시된다.
- 설치주체, 관리유형, 요청주체는 반드시 코드화한다.
- AS 접수는 가급적 설치자산과 연결하며, 연결이 불가능한 경우 임시 접수 후 자산 매핑한다.
- AS 접수 1건은 하나의 Case다. 진행 중 재방문·추가조치·대기(보류)·이관은 같은 접수에 조치 이력을 쌓는다. **완료 후 동일 증상은 재접수**(새 번호)한다. **같은 번호 재오픈은 하지 않는다.**
- 행정·지원 1건은 하나의 Case다(§10.3.2). 다음 행동·조치 이력을 누적하고, **사업명(`work_projects`)과 GTD 복합업무를 섞지 않는다.** 회신 대기와 「할 일(`waiting`)」을 구분한다. 필수 다음 행동·미확인 대기가 있으면 일반 사용자는 완료할 수 없다.
- 처리 완료 시 후속조치와 교체검토 여부를 함께 기록한다.
- 노후도와 장애빈도 기준으로 교체영업 후보를 자동 또는 반자동 산출한다.
- 정기 점검 일정은 자동 초안 이후에도 담당자 수정이 가능하며, 승인 전에는 외부 캘린더에 반영하지 않는다.

## 15. 개발 시 고려사항

- 검색은 기관명, 공식명칭, 담당자명, 제품명, S/N, AS번호 기준으로 빠르게 제공해야 한다.
- 접수 화면에서 고객/설치자산/담당자를 즉시 조회할 수 있는 통합 검색 UX가 중요하다.
- **AS 접수 폼:** 기관을 선택하면 해당 기관의 설치자산 목록을 **콤보박스**로 불러와 선택한다. 자산 미선택(미연결) 접수도 허용한다. `GET /api/assets/:customer_id` 활용.
- **AS 처리 이력 보존:** `as_processes`에 회차별 조치결과·이관 세부·다음 예정일·대기/재방문 사유를 둔다. 접수의 현재 결과코드만 덮어쓰지 않는다. `RECEIPT`/`ACTION_HISTORY` 테이블을 새로 만들지 않는다.
- **행정·지원 GTD:** `work_tasks`를 유지하고 `work_actions`·`work_activities`만 추가한다. `tasks`/`projects` 테이블로 대체하지 않는다. 기존 `task_id`를 보존한다. 반복업무·문서 버전은 2단계.
- **AS 접수 · 요청자:** 기관 선택 시 해당 기관 **담당자 목록**을 콤보로 제시하고, 목록에 없는 이름은 **직접 입력**도 가능하다. `GET /api/contacts/:customer_id` 활용.
- 설치자산 상세 화면에서 최근 AS 이력, 요청 주체, 수행관계가 한눈에 보여야 한다.
- 교체대상 분석은 설치연수, 최근 1년 장애건수, 처리비용, 부품단종 여부를 결합해 확장 가능하다.
- 첨부파일은 설치사진, 점검표, 장애사진, 계정문서, **조치완료보고서** 등 다양한 유형을 지원해야 한다. AS 조치는 파일을 `data/uploads/as/{접수ID}/`에 두고 DB에는 경로·파일명만 저장하며, 화면에는 파일명만 보여 준다.
- **설치자산 사진:** 자산당 최대 3장. 파일은 `data/uploads/assets/{자산번호}/` 폴더에 `{자산번호}_img_{N}` 형식으로 저장한다. 각 사진에 **키워드**를 두어 검색·매뉴얼 활용에 대비한다.
- 개인정보 및 접속정보는 접근권한, 로그기록, 암호화 저장 정책을 적용해야 한다.
- 정기 점검 모듈은 지도 API 의존도를 낮추기 위해 이동시간 **수동 대체 입력**과 **캐시**를 동시에 지원하는 것이 바람직하다.
- 엑셀 월별 캘린더(17.11)는 **병합 셀·스타일·시트 다중 생성**이 필요하므로, 서버에서 xlsx 생성 라이브러리(Go/ Python 등) 선정 시 **스타일 API 지원 여부**를 검증한다.
- **데이터 백업:** 매일 **01:00**(Asia/Seoul)에 `data/` 복사본을 `data/backups/자동백업_YYYY-MM-DD/`에 만든다. SQLite(`app.db`)는 운영 중에도 일관된 스냅샷으로 저장하고, 첨부(`uploads`)도 함께 복사한다. `backups` 폴더 자신은 복사하지 않는다. 서버가 01:00 이후 기동되면 당일 백업이 없을 때 한 번 보정 실행한다. **관리 → 데이터 관리**에서 관리자가 현재 데이터를 같은 폴더에 즉시 저장할 수 있다(폴더명 `수동저장_YYYY-MM-DD_HH시MM분SS초`). 모든 백업은 **목록**으로 관리하고 **정기 백업 / 사용자 백업**을 구분한다. 일 단위 스냅샷은 **최근 14일**만 유지한다. `관리로그_*` 폴더는 14일 정리 대상이 아니다.
- **변경 이력:** 업무 데이터의 등록·수정·삭제는 별도 테이블 `data_change_logs`에 남긴다. **언제, 어떤 데이터, 누가, 어떻게**(등록/수정/삭제)와 변경 전·후 JSON을 기록한다. 수정·삭제는 이력에서 **롤백**할 수 있다.
- **관리 로그 아카이브:** `data_change_logs`는 **3개월**마다 `data/backups/관리로그_시작일-종료일/`로 파일 백업한 뒤 테이블을 비운다(용량이 커지면 이 폴더를 다른 서버·PC로 옮긴다). 기존 백업 폴더의 DB를 열어 **건수·최근 이력 분석**할 수 있다.

## 17. 정기 점검 일정 자동 생성

매월 반복되는 **정기 점검** 일정을 시스템이 초안으로 수립하고, 담당자가 검토·수정·승인한 뒤 개인/팀 캘린더와 연동하는 기능을 정의한다. 기존 **고객기관(사이트)·공간·설치자산** 정보와 연계하여, 사이트별 점검 대상 영역(KLAS / RFID 자동화 장비) 및 장비 수를 반영한다.

### 17.1 목적 및 성격

- 월간 정기 점검 대상이 많을 때 수작업 배열을 줄이고, **지역·이동시간·업무시간** 제약을 만족하는 일정 초안을 자동으로 만든다.
- 자동 생성 결과는 **초안**이며, 반드시 담당자가 현장 상황에 맞게 수정할 수 있어야 한다.
- **승인 완료**된 일정만 외부 캘린더(구글 캘린더 또는 애플 캘린더)에 반영한다. **엑셀 월별 캘린더**는 초안·승인본 모두 보낼 수 있으나, 대외 공유 시에는 승인본 사용을 권장한다.

### 17.2 점검 영역 및 사이트 단위 규칙

| 점검 영역 | 설명 |
|-----------|------|
| **KLAS** | 하드웨어 제품 단위 점검이 아닌 영역으로, **사이트당 표준 소요시간 20분**을 기본값으로 둔다. |
| **RFID 자동화 장비** | 장비(설치자산) 수에 비례한 점검으로, **장비당 표준 소요시간 약 15분**을 기본값으로 둔다. |

- 사이트(고객기관)마다 **KLAS만**, **RFID만**, **둘 다** 대상인 경우가 있다. 기준정보에서 사이트별로 대상 영역을 지정할 수 있어야 한다.
- 사이트별 **점검주기**를 등록한다: **월, 홀수격월, 짝수격월, 분기, 반기, 년1회** (콤보).
- **이번 달 방문 목표(통계·주간보고서의 전체 개수):** 주기가 그 달에 도래하는 사이트마다 점검대상 수만큼 센다. KLAS만=1, RFID만=1, **둘 다=2**. 사이트 수보다 방문 건수가 클 수 있다.
  - 홀수격월=1·3·5·7·9·11월, 짝수격월=2·4·6·8·10·12월, 분기=1·4·7·10월, 반기=1·7월, 년1회=1월, 월=매월.
- 점검 사이트 설정 화면 상단에 **이번 달 주기 해당 사이트 수**와 **방문 건수(KLAS·RFID 합)** 를 주기별로 보여 준다.
- 점검 사이트 설정 목록은 **엑셀 다운로드**로 추출할 수 있다(기관명·표시명·지역·점검주기·KLAS/RFID·유형·고정규칙).
- **자산 기준 일괄 추가**: 설치자산의 **유지보수 계약구분이 유상**이고 **점검주기가 정기 주기(월/홀수격월/짝수격월/분기/반기/년1회)** 인 기관을 점검 사이트로 한 번에 등록한다.
  - 표시명 = 기관명, 지역 = 기관 주소의 시도 축약(충청남도 → 충남), 유형 = 일반.
  - **RFID** = 해당 기관에 제품분류 `rfid` 자산이 있으면 대상, **KLAS** = 제품명·모델명에 `KLAS`가 포함된 자산이 있으면 대상.
  - 한 기관에 점검주기가 여러 개면 **간격이 가장 짧은 주기**를 적용한다(예: 월 + 분기 → 월).
  - 점검주기가 **수시·Call** 이거나 계약이 유상이 아닌 기관은 제외한다.
  - **이미 등록된 사이트는 덮어쓰지 않는다.** 반복 실행해도 신규 기관만 추가되므로 자산 등록 후 다시 실행하면 된다.
- 한 사이트 방문에서 두 영역을 연속 수행하는 것을 기본으로 하되, 일정 편집 시 분리·재배치 가능하도록 한다.

### 17.3 담당 직원 배정

- 월간 정기 점검에는 **전담 직원**을 미리 배정할 수 있다. 배정은 **필수가 아니다.**
- 배정이 없거나 변경이 필요한 경우, **업무 배정 수정** 기능으로 담당자를 바꿀 수 있어야 한다(자동 초안 이후에도 동일).

### 17.3.1 방문 1건의 구성과 완료 처리

방문 1건은 **날짜 · 사이트 · 점검 대상 · 담당자 · 사업명 · 완료 여부**로 이뤄진다.

- **점검 대상**(KLAS·앤로보틱스 등)이 다르면 **같은 날 같은 기관이라도 별도 방문**으로 둔다. 담당자가 다르고 소요시간도 따로 잡히기 때문이다. 중복 방지 기준도 `날짜 + 기관 + 점검 대상`이다.
- **같은 달 · 같은 기관 · 같은 점검 대상은 화면·집계 모두 1건만** 둔다. 방문 예정일을 바꾸면 **바꾼 날짜 칸에만** 나타나고 이전 날짜에는 남지 않는다.
- **사업명:** 방문 추가·수정·조치 화면과 정기점검 업무 화면에서 사업(프로젝트)을 고를 수 있다. `maintenance_visits.project_id`에 저장하고 연결된 일일업무에도 맞춘다.
- **방문 완료**는 방문마다 켜고 끈다. 완료에는 **실제 방문일**이 함께 남고, 비워 두면 예정일을 그대로 쓴다(일정을 조정해 다른 날 다녀온 경우를 위해 별도로 적을 수 있다).
- **지난 방문 일괄 완료**: 기준일을 넣으면 그날까지의 예정 방문을 한 번에 완료로 바꾼다. 이미 완료된 건은 건드리지 않는다.
- 완료한 방문은 **업무 등록 화면의 정기점검 카드에서 빠지고**, 대시보드의 오늘·지연 목록에도 잡히지 않는다. 대신 **완료일 기준으로 완료 목록**에 나타난다.
- **월간 일정 엑셀 적재**: 월별 점검 일정 엑셀(`기관명·구분·제품분류·원담당자·방문예정일`)을 읽어 해당 연도 계획에 방문을 넣을 수 있다. 기준일까지는 완료로 표시한다.
  - 기관명은 **고객 기관명·공식명칭·점검사이트 표시명**과 대조한다. 공백·괄호와 **눈에 안 보이는 문자**를 지우고, 한글은 **완성형(NFC)으로 맞춰** 비교한다(조합형으로 저장된 이름이 섞여 있다).
  - **방문예정일이 없는 행**과 **기관을 못 찾은 행**은 건너뛰고 목록으로 보고한다.
  - 이미 들어 있는 `날짜 + 기관 + 점검 대상`은 건너뛴다. 같은 파일을 다시 넣어도 중복되지 않는다.

### 17.3.2 계획 화면의 보기 방식

한 해 계획(`/maintenance/{계획}`)은 **캘린더 · 칸반 · 목록** 셋 중 하나로 본다(`?view=`). 어느 보기든 **사이트명과 점검 대상을 함께** 적어, 같은 기관에 점검 대상이 둘이면 서로 다른 방문으로 읽힌다.

**방문 수정·삭제** — 일정이 잡힌 뒤에도 **날짜 · 사이트 · 점검 대상 · 담당자 · 사업명 · 표시 유형 · 비고 · 완료 여부(실제 방문일)** 를 고칠 수 있다. 캘린더·칸반·목록의 **수정** / **삭제** 버튼으로 처리한다(중복 일정 정리 포함). 수정 모달에서도 **이 일정 삭제**가 가능하다.

| 권한 | 가능 작업 |
|------|-----------|
| **관리자** | 전체 일정 읽기·방문 추가·수정·완료·삭제, 지난 방문 일괄 완료. 연도 계획 생성·삭제, 자동 배정, 승인/승인 취소 |
| **기술담당**(현장 담당자) | **기본은 본인 배정 일정만** 표시. 방문 추가·수정·완료·삭제, 지난 방문 일괄 완료(본인 범위). **전체 일정 보기** 버튼으로 타 담당자 일정 조회(조회 중에도 수정·삭제 가능). **내 일정만 보기**로 복귀 |

| 보기 | 내용 |
|------|------|
| **캘린더**(기본) | 해당 달의 월력. 칸마다 `사이트 · 점검 대상`과 담당자, 완료 표시. **점검 대상 색:** 초록=앤로보틱스, 파랑=K-LAS(KLAS), 보라=세종 K-LAS. 칸에서 바로 완료 처리 |
| **칸반** | **예정일 경과 / 오늘 / 예정 / 방문 완료** 4열. 카드에 사이트·점검 대상·날짜·담당자와 완료·삭제(색은 점검 대상과 동일) |
| **목록** | 날짜·사이트·점검 대상·담당자·상태 표. **전체**(연간)를 볼 수 있는 유일한 보기. 점검 대상은 색 뱃지 |

- 화면 **상단**에 **일정 배정안됨**을 둔다. 이번 달(보고 있는 달) 점검주기에 해당하는데 **아직 방문일이 없는** 사이트×점검대상(KLAS·RFID 각각 1건)을 나열하고, 날짜를 넣어 바로 배정할 수 있다.
- 달 선택은 1~12월 탭으로 한다. 캘린더·칸반은 한 달만 보므로, 달을 안 고르면 **올해 계획이면 이번 달**, 지난·다음 해 계획이면 **방문이 있는 첫 달**을 연다.
- **방문 추가**와 **지난 방문 일괄 완료**는 화면 위 **버튼**으로 두고 팝업에서 입력한다(표 아래 상시 노출하지 않는다).
- 완료·삭제 후에는 **보던 보기와 달로 되돌아온다.**
- **엑셀 월별 캘린더**에도 `사이트 · 점검 대상`으로 적는다(§17.11.2).

### 17.4 경로·지역·이동 시간

- **이동 경로 및 일자 배치** 시 **지역별로 묶어 계획하는 것을 최우선**으로 한다(동일 권역 내 방문 순서 최적화).
- 사이트 간 **이동 소요 시간**은 원칙적으로 **네이버 지도(또는 동등한 경로·거리 API)** 를 통해 산정한다.
- **구현이 불가능한 경우**(API 미계약, 정책 제한 등): 담당자가 **사이트 쌍 또는 지역 간 표준 이동시간**을 수동 입력·관리할 수 있는 대체 수단을 제공한다.

### 17.5 일일 운영 제약(하드 제약)

| 제약 | 내용 |
|------|------|
| 출발 | 매일 **09:30 ~ 10:00** 사이 **사무실 출발**을 기준으로 한다(설정값으로 조정 가능하나, 기본은 이 구간). |
| 종료 | 당일 **마지막 현장 도착**은 **17:00 이전**이어야 한다(현장 체류·점검 시간 포함해 17시 전 종료 가능하도록 역산). |
| 비근무일 | **토·일 및 공휴일**에는 일정에 넣지 않는다. 공휴일 데이터는 **대한민국 공휴일 캘린더**(또는 관리자가 등록한 휴무일)를 사용한다. |

### 17.6 월간 목표일 및 사이트 고정 규칙

- **예외(고정일·지정일 사이트)** 를 제외하고, 월간 정기 점검 전체가 **매월 25일 이전에 마무리**되는 것을 목표로 일정을 수립한다.
- 일부 사이트는 **특정 요일·주차** 등 고정 규칙이 있다. 예: *국립세종도서관 — 매월 마지막 주 월요일*. 이런 규칙은 **사이트별 점검 일정 규칙**으로 등록하고, 자동 생성 시 **해당 슬롯에 고정 배치**한 뒤 나머지 사이트를 채운다.

### 17.7 자동 수립 로직(요구 수준)

시스템은 최소 다음 순서를 만족하는 알고리즘(또는 이에 준하는 휴리스틱)을 적용한다.

1. 고정 규칙 사이트를 해당 월의 유효한 법정근무일에 배치한다.
2. 잔여 사이트를 **지역** 단위로 클러스터링한다.
3. 각 근무일에 대해 사무실 출발 시각(기본 09:30~10:00)부터, **이동시간 + 현장 소요시간**을 누적하여 배치하며, **17:00 전 마지막 도착·종료**를 넘지 않는 선에서 일자를 나눈다.
4. 동일 일자·동일 권역 내 방문 순서는 이동시간 합이 작아지도록 정렬·최적화한다(정확한 TSP 필수는 아니나, 무리한 왕복을 줄이는 수준 이상).
5. **25일 이전** 완료가 불가능하면 **경고·미배치 목록**을 생성하고 담당자가 수동으로 조정한다.

### 17.8 수정·승인·버전

- 자동 생성 직후 상태는 **초안**이다. 담당자는 **날짜·순서·담당자·현장 시간**을 수정할 수 있어야 한다.
- **승인** 절차(승인자·승인 시각)를 두어, 승인된 버전만 외부 연동·대외 공유의 기준이 되도록 한다.

### 17.9 캘린더 연동

- **승인된 일정**에 한하여 **구글 캘린더** 또는 **애플 캘린더**에 등록할 수 있어야 한다.
- 연동 방식은 구현 단계에서 확정하되, OAuth(구글), CalDAV/구독 URL(애플) 등 **표준적 수단**을 우선 검토한다. 개인 계정/공용 팀 캘린더 여부는 운영 정책으로 정한다.

### 17.10 데이터·기준정보 연계(구현 시)

- **사이트**: 고객마스터(기관)와 1:1 또는 명시적 매핑.
- **지역**: 주소·시도·권역 코드 등 기준정보 또는 별도 **권역 마스터**.
- **RFID 점검 시간**: 설치자산 중 해당 분류 장비 수 × 기본 15분(사이트별 오버라이드 가능).
- **KLAS**: 사이트당 20분 기본(오버라이드 가능).
- **이동시간**: API 결과 캐시 + 수동 보정 테이블.

### 17.11 엑셀 월별 캘린더 출력(유지보수계획표)

현업에서 사용하는 **유지보수계획 엑셀**(월별 달력 형태)과 **동등한 정보 구조·가독성**을 갖춘 파일을 시스템에서 생성·보내야 한다. 참고 레이아웃: 상단에 연·월 제목, 요일별 7열 격자, 날짜 칸에 사이트명 다줄 표기, **1월~12월 시트 분리**, 글자색으로 방문 유형 구분.

#### 17.11.1 파일·시트 구성

| 항목 | 요구 |
|------|------|
| 시트 | **12개**: 시트 이름 `1월` … `12월`(해당 **연도** 기준). 활성 시트는 사용자가 열 때 해당 월로 두어도 되고, 기본은 `1월` 또는 “오늘이 속한 월”로 둘 수 있다. |
| 파일명 | 예: `YYYYMMDD유지보수계획.xlsx`. 날짜·연도·버전 규칙은 운영 정책으로 정하되, **다운로드 시점 또는 계획 기준일**이 식별되도록 한다. |
| 인코딩·글꼴 | 한글 사이트명이 깨지지 않아야 하며, Windows Excel 기본 환경(예: **맑은 고딕**)에서 정상 표시된다. |

#### 17.11.2 달력 격자(각 월 시트)

- **열 머리글**: **일요일, 월요일, … 토요일**(한글 요일명, 왼쪽부터 일요일 시작).
- **월 표제**: 해당 시트 상단에 **연·월**을 크게 표시한다. 예: `2026년 3월`. 제목은 눈에 띄게(글꼴 크기·**녹색 등 강조색**) 구성할 수 있다.
- **날짜 칸(셀)**:
  - 칸 **상단 왼쪽**에 해당 일의 **일자(숫자)**.
  - 그 **아래**에 그날 방문 예정 **사이트 표시명**을 **줄바꿈**으로 나열한다. 한 날짜에 **복수 사이트**가 있으면 모두 표기한다. **점검 대상이 적힌 방문은 `사이트 · 점검 대상`** 으로 적어, 같은 기관을 두 번 가는 건이 구분된다.
- **해당 월에 속하지 않는 칸**(앞뒤 빈 칸)은 비우거나 배경만 구분해 달력 형태를 유지한다.

#### 17.11.3 비근무일·빈 칸

- **토요일·일요일 및 공휴일**(17.5와 동일 데이터 기준)에는 **점검 일정을 넣지 않는다**. 필요 시 해당 칸에 **회색 배경** 등으로 휴무임을 표시할 수 있다.
- 일정이 없는 평일 칸은 비워 둔다.

#### 17.11.4 글자색·점검 대상 구분

화면·엑셀 모두 **점검 대상(제품)** 기준으로 색을 나눈다. 구체 색상 코드는 테마로 조정 가능하나, 기본 정의는 다음과 같다.

| 점검 대상 | 표시 예 | 설명 |
|-----------|---------|------|
| **앤로보틱스** | 초록 계열 | RFID 자동화 등 앤로보틱스 점검 |
| **K-LAS** (표기 `KLAS` 포함) | 파랑 계열 | 일반 K-LAS 점검 |
| **세종 K-LAS** | 보라 계열 | 세종 관련 K-LAS 점검 |

점검 대상이 비어 있을 때만 예전 엑셀 유형(일반=녹색·고정=적색·사무소=청색)을 보조로 쓴다.

#### 17.11.5 데이터 일치

- 엑셀 내용은 화면의 **월간 정기점검 일정**과 **동일한 배치 결과**를 반영해야 한다. 화면에서 수정한 뒤 파일을 다시 받으면 **수정 반영본**이어야 한다.
- 선택 기능: 파일 상단 또는 시트에 **연도·작성자·승인 여부** 등 메타정보 행을 넣을 수 있다.

#### 17.11.6 구현 시 참고(비기능)

- 셀 **자동 줄바꿈**, **행 높이·열 너비** 조정로 다줄 사이트명이 잘리지 않게 한다.
- 인쇄 시 가독성을 위해 **가로 방향(A4/A3)** 프리셋을 제공할 수 있다(선택).

## 18. 결론

고객지원 시스템의 성공 여부는 AS 화면보다 먼저, 기준정보의 완성도에 달려 있다. 따라서 본 시스템은 고객기관, 공간, 담당자, 설치자산, 수행관계 정보를 중심으로 설계해야 하며, 이를 토대로 AS 접수·처리·현황을 안정적으로 운영해야 한다.

또한 축적된 데이터는 단순 운영 기록에 머무르지 않고, 타사 납품 자산의 교체시기 파악과 당사 교체영업 제안으로 이어질 수 있어야 한다. **정기 점검 일정 기능**은 이러한 기준정보(기관·위치·자산)를 활용해 현장 운영 효율을 높이는 확장 축이며, **엑셀 월별 캘린더**로 기존 유지보수계획 관례와 맞춘 공유·보관을 지원한다. 본 기획서는 이러한 목적에 맞춘 고객지원 시스템의 기준 모델로 활용한다.
